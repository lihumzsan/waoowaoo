# System Journey Coverage Architecture Incident

## Classification

This is a class-D Architecture Incident. The repository previously treated a
large collection of isolated tests as product evidence, while the first real
browser-complete Assistant journey immediately exposed cross-process failures.
The current Golden system is valuable but owns only one product family: the
Assistant-driven edit-first story-to-video workflow. It is not yet evidence for
the other P0 user results exposed by the product.

## Goal

Build and execute one browser-driven product-journey system that:

1. starts from real user entry points and reaches independently defined user
   results;
2. executes production UI, authentication, API routes, services, MySQL, Redis,
   queues, workers, storage, Outbox, SSE, and reload recovery;
3. uses canonical checkpoints generated by the real mainline to continue
   downstream discovery after an earlier blocker;
4. observes the browser, network/background errors, and read-only durable facts;
5. records every reproducible product or harness failure before any permanent
   repair;
6. completes the discovery pass before clustering symptoms into shared
   architectural root causes;
7. removes every temporary diagnostic bypass before final verification.

## Non-goals and prohibited scope

- Do not define when tests run in commit, push, pull request, nightly, or release
  workflows.
- Do not promise or infer 100% behavioral coverage.
- Do not add one test per route, file, component, operation, or task type.
- Do not mock production UI, route, service, state machine, database, queue,
  worker, SSE, projector, or billing owner to manufacture product success.
- Do not hand-build workflow checkpoints in business tables. Checkpoints must be
  produced by the real workflow and forked through the production Workflow Lab.
- Do not use translated copy as the sole lifecycle oracle. Copy may prove user
  comprehension, while stable identities and durable facts prove business state.
- During discovery, files owned by the separate Assistant repair were treated
  as read-only. Final integration is now explicitly authorized: formal repairs
  are merged first, then the original Journey scenarios are the acceptance path.
- Do not replace AI-initiated actions with a server-side hard-coded workflow
  continuation.

## Discovery before repair

The discovery pass follows this loop:

1. execute the longest real mainline or an independent P0 journey;
2. capture trace, screenshot/video, browser/network observations, service logs,
   and read-only durable facts at the first unexpected boundary;
3. register the failure in `bug-ledger.md`;
4. continue downstream from a canonical checkpoint generated by the real
   mainline;
5. only when no checkpoint exists, use a clearly marked `TEMP-DIAGNOSTIC`
   change in this isolated worktree, record its diff and affected evidence, and
   never deliver it as a permanent fix;
6. continue until every admitted P0 journey reaches its user result or has an
   explicit external/environmental blind spot.

Permanent repair begins only after the discovery map is sufficiently complete.
Symptoms are then grouped by invariant, owner/writer, identity, lifecycle,
transaction boundary, retry owner, and recovery responsibility. Each repair
must remove competing authority or an invalid heuristic, not merely add a
special case.

## Evidence channels

| Channel | Authority | Required evidence |
| --- | --- | --- |
| User result | Product journey contract | Stable page identity plus the intended result visible to the user |
| Durable state | Production persistence owners | Read-only project, episode, run, interaction, operation, task, billing, resource, and event facts as applicable |
| Runtime health | Browser and process observations | Page errors, console errors, failed requests, unexpected 4xx/5xx, worker/app exits, and blocked external calls |
| Duplicate effects | Canonical identities | Duplicate message, tool call, task, resource, charge, or generation identities |
| Recovery | Production reload/resume path | Same stable boundary before and after reload, disconnect, retry, or process restart |

## Worktree and ownership boundary

- Goal branch: `codex/system-journey-coverage`.
- Baseline: committed `fa7271674` (`exp/assistant`), which already contains the
  Golden Journey and test-system reset commits.
- Integrated owner: the Assistant repair commits and this Journey incident are
  consolidated on `exp/assistant`; unresolved ledger rows are repaired there and
  re-run through their original browser paths.
- Generated artifacts, provider bytes, credentials, and environment descriptors
  remain ignored local evidence and must not enter Git.

## Implementation stages

1. Prove the harness is isolated and fail-closed for concurrent worktrees.
2. Inventory real product journeys and publish the journey/risk map.
3. Replace copy-only lifecycle observations with stable browser identities and
   read-only durable assertions.
4. Execute the existing longest mainline and preserve the first red baseline.
5. Produce canonical checkpoints from the real mainline and run downstream
   probes even when an earlier stage is blocked.
6. Add only distinct P0 journeys and high-risk transition variants admitted by
   test governance.
7. Complete the discovery ledger, then cluster and repair architectural roots.
8. Re-run the original journeys, remove all temporary bypasses, and retire tests
   that have no independent oracle.

Actual command results and executed/not-executed counts are maintained in
`execution-log.md`; scenario registration or `--list` output never counts as a
behavior pass.

The retained Unit/Integration inventory and deferred internal-mock ownership
are recorded in `test-asset-audit.md`; mock presence alone is not a deletion
rule.

## Completion boundary

This incident is complete only when the journey/risk map identifies the status
of every admitted P0 result, all mounted scenarios were actually executed or
have an explicit blind spot, every registered critical failure is either fixed
and reverified or externally blocked, no `TEMP-DIAGNOSTIC` remains, and the
final report includes scenario counts, pass/fail/skip results, root-cause
groups, deleted authorities, residual risks, and external-provider boundaries.
