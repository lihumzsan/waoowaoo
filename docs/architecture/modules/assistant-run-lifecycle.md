# Assistant Run 生命周期

## 设计理念

Assistant 是受服务端运行时约束的决策者，不是流程状态的权威来源。一次 run 的开始、等待、任务关联、恢复、结算和失败必须由服务端持久状态与锁协调；模型消息、UI 文案或工具输出不能自行宣告流程已完成。

## 不变量

- **AR-01 — 服务端权威。** thread/run 的 append、终态、锁和恢复由服务端管理；客户端和模型不得持有第二套 run 状态。
- **AR-01A — 不存在 Workflow 或主链状态。** Assistant 的唯一能力表是完整 Operation registry；项目快照只提供持久事实和能力约束，不提供 `step/status/recommendedAction`。Primary Agent 每次依据用户目标、精确 Resource、Task 终态、输入 prerequisite、owner/scope、provider capability、Approval/Choice 与 Run fence 自主组合 Operation。不得恢复 WorkflowView、阶段、固定下一步、持续时间分支、operation group、UI gating 或任何第二状态机。
- **AR-01D — Agent Plan 只是线程便签。** `update_plan` 是当前 Assistant Thread 活动计划快照的唯一写入口，每次调用完整替换，最多一个步骤为 `in_progress`。持久非空快照必须至少包含一个 `pending` 或 `in_progress` 步骤；空列表或全部步骤均为 `completed` 都由同一入口规范化为 `planJson=NULL`，后续模型输入与 Session View 均不再包含该计划。快照不得驱动 Operation eligibility、Task/Wait/Approval/Choice、Workflow、Resource/Artifact、Canvas 节点或 Run 终态，也不得恢复 `PlanRun`、任务依赖或第二套执行状态机。模型自主判断步骤完成，UI 只展示服务端快照，不从历史消息、Tool output 或本地完成判断重建，也不得用 spinner 把 `in_progress` 伪装成仍在运行的 Task/Run。
- **AR-01E — 设置不形成 Agent 模式。** Assistant 没有 Ask/Auto 执行模式，客户端不得向 chat/control 传递权限模式，Prompt 也不得据此改变工具可用性。破坏性 Operation 始终使用 SDK Approval，Choice 始终属于用户决定；`UserPreference.assistantBillingConfirmationRequired` 只决定新收费调用是否创建报价 Interruption。关闭时 runtime 仍为本次 Tool call 创建不可变 plan/quote 与精确 Grant，再复用唯一收费提交入口；既有 pending Approval 继续按原 Grant 恢复，不被设置变化自动消费。
- **AR-01F — Creative Subagent 只复用 Task，不形成第二 Agent Run。** 主 Agent 只能通过注册式 `delegate_creative_work` 委派专业创作推理；严格 `delegation.source=requests|chapters` 联合经统一 Task submitter 为每个逻辑请求创建一个 `creative_work` Task。`Task.id` 是唯一 Subagent identity，`Task.status` 是唯一生命周期事实；Worker 只在某个 Task attempt 内运行一次无状态模型循环，初始只看到 output registry 绑定的一个专业 Skill 目录项，并且只能调用 `read_skill` 读取该知识。Worker 模型只由服务端正式 `analysis` 角色配置解析并冻结到 Task，Primary Assistant 模型、Agent 输入、output kind 和 Worker 均不得重新选模；Primary 不指定 Skill；output registry 的 `professionalSkillId` 是服务端唯一绑定与门禁。Worker 没有 ProjectAgent Run/Thread、Operation、Wait、Approval、Choice、Resource、Canvas 或领域数据库写权，结果也不裁决项目状态。多个 Subagent 只复用当前模型步骤既有 `OperationBatch + collecting Wait`，全部终态后只由既有 Outbox continuation 恢复主 Agent 一次。完整 strict 结果保存在 `Task.result`；Session 生命周期与 continuation 只能收到 TaskDefinition 的 reference projection，需要正文时主 Agent 通过正式 `get_task(taskId)` 读取。禁止恢复同步 Tool 内 Worker、Activity identity、`subagent.progressed` writer、独立 Subagent Run/Thread/Batch 或第二套恢复协议。真实执行仍由主 Agent 的完整 Operation registry 单入口完成；Operation、Canvas、Approval/Choice、计费与 Run fence 均保持既有权威入口。
- **AR-01C — Operation Schema 是模型调用的唯一参数契约。** 每个 tool-channel Operation 必须从自己的 canonical strict runtime schema 生成一份完整 `toolInputSchema`；registry 中这份投影同时服务 direct Tool、`load_tools` 和 `execute_operation`，不得按模型、项目配置或 execution segment 再绑定第二份 Schema。固定 `execute_operation` 只有 `operationId + argumentsJson` 两个必填字段，不存在 `kind`、`contractId`、revision、loaded ticket 或 static/bound 分支；服务端始终用 registry 的 canonical runtime schema 与同源 `toolInputSchema` 规范化。不得把必需参数藏在空 object、`unknown`、passthrough、根级 refinement 或 Prompt 文案中。配置与 capability 是 planner 的服务端输入：planner 解析正式 modelKey 和项目配置、按生产 capability registry 校验产品字段，并把 model/options 冻结进 PlanSnapshot、报价、Task payload 与 provenance；它们不得改变模型调用协议或形成第二 Schema writer。模型可选 capability 值可用显式 `auto` 表达“系统决定”，服务端已知唯一答案的字段（如 aspectRatio）不得出现在模型可见 Schema，只由 planner 注入。strict transport 把 canonical optional 投影为 nullable 时，null-to-absence normalizer 只能依据同一 canonical schema 解释；归一化后仍不满足 canonical schema 必须抛出带 issues 与 corrections 的 typed `OPERATION_INPUT_INVALID`。条件输入必须使用可穷尽 discriminated branch。批准后的收费执行只消费 PlanSnapshot 的 `normalizedInput`，恢复路径不得重新归一化。Main Agent 不提交模型或 Provider 原始字段；实际模型仍由正式配置 owner 解析。
- **AR-01H — Tool 前缀固定，常用 Schema 直接提供，其余按需读取。** `Operation registry → toolset` 是唯一、穷尽的能力权威；`toolExposure=direct|on_demand` 只声明传输方式。每个模型步骤只看到固定 `load_tools + execute_operation` 与 registry 明示的少量 direct Operation；加载不改变顶层工具数组。`tool-discovery.ts` 只从 registry 读取 on-demand Operation 的 canonical `operationId + description + parameters`，不创建、保存或校验任何临时执行身份。`execute_operation` 不以“是否加载”作为权限或状态门槛，只把精确 Operation identity 与参数交给同一个 Operation executor；历史加载结果可以继续作为 canonical Schema 知识。Approval 恢复只消费持久化的 normalized snapshot。`load_tools` 不属于 Operation、不执行领域动作、不写持久状态、不参与 outcome/stop/batch/approval，也不进入用户可见 Tool stream。
- **AR-01G — 项目画幅是一个普通、可空的项目事实。** `Project.videoRatio` 不得有数据库、config service、project create 或媒体 Operation 的隐式默认；不存在专用 `confirmedAt/version` 状态。`update_project_config` 是唯一 writer，只接受模型显式提交的 ratio，不从用户文案 substring 猜确认。画幅缺失且当前媒体请求需要它时，Primary 可发起模型填写的通用 Choice，并将当前选择原子 commitment 到 Choice-eligible `update_project_config`；该 commitment 只写当前画幅，不授权或启动媒体。所有项目图片/视频 plan 冻结当前 `ratio + fingerprint`，重放时重新读取同一事实并比较内容；媒体请求中的显式 aspectRatio 必须与项目事实一致，禁止局部覆盖。global Asset Hub 不属于项目交付画幅，明确豁免。
- **AR-01B — HTTP Command 单入口。** 用户消息、Approval response 与 Choice response 必须先由各自 route 完成一次鉴权和输入解析，再统一调用 `executeProjectAgentCommand`。只有该 service 可以为 HTTP command 编排当前 command、Run slot/identity、Redis lock/heartbeat、Run create/retry、Interruption consume、runtime invocation 与 pre-stream failure settlement；它不得读取 UI Thread 再重建模型历史，跨 turn 历史只属于 AR-02H 的 SDK Session。route 不得导入 runtime/Run/lock/Interruption owner，不得构造私有 `NextRequest`、header 或 body 再调用另一 route。service 只组合现有 owner，不直接实现模型、Operation、Billing、Task Terminal 或 execution handoff。Task terminal continuation 仍只属于 AR-03B 的 Outbox 入口，不得为追求形式统一改走 HTTP service。

  control 命令的准入必须先解析持久目标，再决定 Run slot 与 lock：目标 interruption 已 `consumed/superseded` 且不满足既有同响应重试条件时，service 返回 typed `PROJECT_AGENT_CONTROL_ALREADY_RESOLVED` 平静响应（HTTP 200 JSON，携带目标 run/interruption 最新状态），绝不因 scope 内另一个活跃 Run 抛 `PROJECT_AGENT_RUN_ACTIVE`；目标仍可行动时 slot 检查以 `excludeRunId` 排除目标 run 自身，Redis lock 经 control 专用 acquire-or-adopt 入口对同 runId 的残留 lease 轮换 token 接管——旧持有者 renew/release 因值不匹配失败并按 AR-05B 心跳失权中止，不同 runId 的 lease 永不被接管。禁止恢复"先 slot 检查后解析目标"的旧准入顺序。
- **AR-02 — 每回合有结算语义。** 一个前台 turn 必须明确是完成、等待用户、继续 Agent 还是失败；合法的空输出或未发起新 Tool 可以结算为 `completed` 且不产生领域事实，只有 completion、Tool、持久化、ownership 或协议本身失败才可结算为失败。Task 提交只产生 durable receipt 与独立后台 Run/Wait，不把当前前台 Run 改成等待 Task；模型文案不得伪造领域完成。
- **AR-02A — 只有一个通用 Choice。** `request_choice` 是唯一 Choice 发起入口。Primary Agent 必须为当前一个决定填写完整本地化卡片内容、交互模式、候选组、稳定 option value、可选精确 subject 和可选 commitment；服务端只补 run/interruption/card/tool identity。协议不存在 `choiceType`、领域卡片 registry、Workflow 触发器或服务器从文案猜测的卡片。Choice 不得承诺、命名或自动启动后续步骤。
- **AR-02B — Choice Offer 单一权威。** `request_choice` 先把完整不可变 Offer 与模型原始 `subject/card` 参数持久化为 `ProjectAgentExecutionHandoff(kind=choice)`；唯一 settlement 在同一事务写入可见 `ProjectAgentInterruption.payload`、assistant message、模型 Session snapshot 与 Run 等待状态。Offer 同时包含身份、完整卡片、精确 subject fingerprint 和零个或多个当前决定 commitment。首屏与刷新只投影该 Offer；不得从当前 Resource、历史消息、DOM 或专用领域表重建卡片。若进程在 SDK 持久化 Tool 输出前死亡，恢复只能用该 handoff 中的完整原始参数补齐同一个 `function_call/function_call_result`，不得生成空参数占位或重新调用模型。
- **AR-02C — Choice 回答原子消费。** control 只提交 interruptionId、cardId、toolCallId 与原始回答。服务端同一事务严格解析持久 Offer、校验身份、重读 subject fingerprint、把回答规范化为 `confirm | select | text | cancelled`、消费 interruption、记录 Event 并开始唯一 response execution segment。`cancelled` 只表示用户关闭当前 Choice，不取消 Run、Task 或已提交副作用，也不匹配任何 commitment；Primary 从该明确结果重新规划、等待或交付。cancelled 不消费 subject,因此必须在 subject fingerprint 复核之前短路——offer 过期恰恰是它要解除的场景(stale pending Choice 会无限期 defer 同 scope 续跑),其余三种回答仍必须通过 fingerprint 复核。任一身份、fingerprint、回答或命令校验失败必须整体回滚，Choice 保持 pending。
- **AR-02D — 可选 commitment 只提交当前 Operation。** Offer 可以没有 commitment；此时回答只恢复 Primary Agent。只有模型在 Offer 中明确冻结、且目标 Operation 在 registry 声明 `choiceCommit.enabled=true` 的确定性、非收费、事务型写入，才可随匹配的 confirm/option 在 Choice 消费事务中复用唯一 Operation invocation 原子提交。自由文本永不执行 commitment；一次回答至多匹配一个 Operation；不得把当前决定扩展为后续链、媒体 Task、收费授权或第二 writer。
- **AR-02E — 最终消息、模型历史与 Run 终态原子结算。** 普通 Run 的 assistant message、ready SDK Session snapshot 与 `completed/failed/cancelled` Event 必须由 `settleProjectAgentRunWithMessage` 在同一事务提交；任一写入失败时终态不得前进。Choice/Approval/continuation 通过 execution handoff 复用同一提交语义。前台消费者取消流时，取消终态必须先于通用 settled cleanup 提交，然后才能停心跳并释放 Run lock；HTTP request 断开只是进入同一终态的另一个 signal。两者都不得取消已提交的后台 Task/Wait。Thread aggregate 以版本化 Session snapshot 和消息 append 分别维护模型事实与 UI 投影，禁止并发用户消息、普通 Run 和 continuation 通过 read-modify-write 相互覆盖。
- **AR-02F — 通用卡片策略由 Offer 自描述。** 持久卡片显式声明 `mode`、`replyMode`、group `presentation`、是否允许组内自由文本以及所有用户可见文案。通用 renderer 只能消费这些字段，不得按 group key、候选内容、领域类型或历史消息私自解释交互和布局。新增选择场景只增加一次 `request_choice` 调用，不新增协议类型、renderer dispatcher、route 或写入入口。
- **AR-02H — SDK Session 是唯一模型历史，模型输入只有一个裁判。** 跨 turn 模型历史的唯一 canonical representation 是 `ProjectAssistantThread.modelHistoryJson` 中由通用 Agents SDK `Session` 读写的完整 `AgentInputItem[]`；它必须原样保留 user/assistant message、reasoning、Tool call、完整 arguments、Tool result 与 provider metadata。`messagesJson/UIMessage` 只服务 UI 展示，绝不能反向转换、筛选或补写模型历史；当前 command 只把本轮 user/Choice/Task 输入交给 runner，由 SDK 与 Session 合并历史。Choice 回答是新的 canonical user item，原始 `request_choice` call/result 继续保留在 Session，禁止合成空 arguments 的 Tool call。

  Session 在 execution segment 运行中只向 thread 的 pending snapshot 写入；pending 绑定 `executionSegmentId + baseVersion`，SDK 产出模型 item 后才标记 ready。普通 Run settlement 或 execution handoff 是模型历史终态的唯一入口：正常完成、合法 Tool 失败与持久 Choice/Approval 必须在同一事务把 exact ready pending snapshot 连同 UI message 与 Run/Event 晋升为 committed；网络/stream 错误、取消、失权、delivery exhausted 与 outcome unknown 必须在同一事务只丢弃经 `run.execution_started` 或 continuation checkpoint 证明属于本 execution segment 的 pending。版本、segment、ready 或内容任一不一致都 fail closed；不得把不完整 snapshot 强制标记 ready，也不得遗留 pending 阻塞下一 segment。准备完成的 Choice/Approval 可从 durable handoff 恢复同一 snapshot；任何终态都不能覆盖 committed 或其他 segment。旧 Thread 不从 UI 历史 backfill，首次运行从空 Session 明确开始。

  「这一步发给模型什么」只由 `model-input` filter 裁决，并覆盖 initial user turn、Decision resume 与 Task continuation 的每次请求。预算只来自 `resolveProjectAgentModelInputBudget`：`min(平台上限, 模型声明 contextWindow)` 减去 instructions、tool schema、预留输出与余量，不存在 48K/24K 或“老化会话”第二阈值。未超 `availableInputTokens` 直接调用；超限时先让同一 filter 清可重新读取的 Tool result，仍超限才由 runtime 在稳定执行边界调用一次 `context_compress`。该动作把当前完整活跃 Session 历史重写为一个有输出上限的 `context_checkpoint`，成功后追加到同一 canonical Session；原始 items 不删除，model-input 只投影最新 checkpoint 及其后内容。未来再次超限时用旧 checkpoint 与新增历史重写一个新 checkpoint，允许合并、去重和删除已推翻事实，禁止逐字追加旧 checkpoint。同一 execution segment 不循环压缩；压缩失败或压后仍超预算 typed fail。project state 与 Plan 仍是瞬时 system input；canonical Tool 定义不因 segment 失效，也不存在 discovery contract 专用过滤。预留耗尽必须 typed fail，禁止发送超限请求。

  用户消息图片在 canonical Session 中只保存精确附件 marker（签名 attachment receipt + 预定 Resource ID），不保存受保护 `/m/` 地址、临时签名 URL 或像素副本。每次模型请求必须由同一个 input filter 重新验证 receipt 的 owner/project 签名并回读登记 MediaObject，再经共享 outbound-image authority 投影为当次 `input_image`；SDK 把过滤后 payload 回写 Session 时，Session writer 必须先还原 marker。缺失、越权、非图片、媒体事实不一致或无法安全出站必须原地失败。已退役的 resource-backed marker 属于协议不兼容历史：outgoing payload 将其替换为显式占位文本并记录结构化日志，绝不再解析为媒体，也不静默丢弃。音频附件目前只提供附件 metadata，不能伪装成已传给模型的音频本体。

- **AR-02G — 决定不可重开，执行段可恢复。** Approval/Choice 一经 `consumed` 就是不可变事实。一个 Run 可包含 initial user turn、Decision resume、Task continuation 多个执行段；`run.execution_started` 必须绑定明确的 `executionSegmentId`（user Run、interruptionId 或 continuation commandId），不可再用 runId 代表所有执行。持久 execution-started identity 是 Redis lock 之外的数据库围栏；同一 segment 再次申请必须在模型输入裁决、模型调用和 Tool 执行前显式拒绝并按 outcome unknown 处理，不得把幂等 Event replay 当作新的执行许可。初始 user-turn 的水位不得阻止尚未开始的 Decision retry。
- **AR-03 — Task 终态驱动继续。** Task 成功/失败后的唤醒只由持久任务终态触发，并以幂等方式关联到对应 run。
- **AR-03C — 一个模型步骤的 OperationBatch 与唯一后台 Wait 原子交接。** 一个模型 step 可以发出多个独立 Tool call，也可以多次调用同一个 Operation；成员身份是 opaque `toolCallId`，不得用 operationId 去重。所有实际提交 Task 的成员共享一个 `OperationBatch(batchId)`、一个独立 `backgroundRunId` 和一个 collecting Wait；每个成员仍通过自己的 Task/批准计划事务，把 Task、billing freeze、Created Event、lifecycle/enqueue Outbox 与该成员的 Wait membership 一次提交。SDK Tool commit callback 可以为数据库围栏串行执行，但已提交 Task 彼此并行，不能把 commit 串行误解为后台执行串行。模型步骤结束时 runtime 只 seal 一次完整 Task 集；Task 在 seal 前先终态时不触发 continuation，seal 必须锁定真实 Task 并折叠这些早到终态。seal 后 Wait 行是整批终态聚合的唯一事实；全部成员无论成功、失败或取消，最后一个终态都只创建一条 continuation command，不存在按 Operation 配置的静默完成分支。成员提交后只向前台模型返回 durable Task receipt；前台 Run 继续工具循环或正常回复，用户也可在后台 Run `awaiting_task` 时开启新前台 turn。不得每 Task 建 Wait、首个成员完成就恢复、以 operationId 禁止重复调用、提交后猜 membership，或把后台 Wait 当成全局对话锁。
- **AR-03F — 并行 Tool 失败是一轮纠错机会。** stop controller 以一次模型 step 为纠错计数单位；同一步中无论有多少并行成员失败，run-level error budget 只增加一次，同一 Operation 的 per-operation budget 也只增加一次。下一模型 step 再次失败才算新的尝试。`OPERATION_NOT_ALLOWED/NOT_FOUND/PLAN_CHANGED/OUTPUT_INVALID` 等 fatal code 仍可在首个失败 step 立即停止；错误事实和所有成员结果仍逐项保留，不能用聚合计数覆盖或伪造成功。
- **AR-03B — Continuation 单入口、at-most-once 模型围栏与原子交接。** Task 终态续跑只能由 Outbox worker 消费 `PROJECT_AGENT_CONTINUE_WAIT` 命令启动。最后一个 Task 终态事务提交后，Terminal Service 应立即把本事务创建的精确 Outbox command 加入运输队列；失败不回滚业务终态，持久 Outbox dispatcher 仍是崩溃恢复 owner，不能把周期扫描当正常延迟。命令 ID 同时作为 claim、execution segment、模型 request 与消息幂等身份；它不是 `ProjectAgentActivity`。开始续跑时必须先检查数据库 Run slot，再取得同 scope 的 Run lock；slot 检查只能排除 continuation 自己的后台 Run，必须清理其他 stale `running` Run，并在另一前台 Run 正在执行或等待 Approval/Choice 时保持投递可重试。此类占用是 typed defer，不是 delivery failure：Outbox 必须原子释放 lease、撤销本次 deliveryCount、保留非 dead 命令并设置下一次 `availableAt`，本次 BullMQ job 正常结束后由既有 dispatcher 重新投递，禁止消耗有限失败次数。Outbox 与 continuation claim 使用短租约并持续 heartbeat；进程死亡后只等待租约过期，不得依赖十分钟级租约隐藏停顿。Redis lease 已释放不能覆盖仍 fresh 的数据库 `running` 事实，不得并发写同一 Thread。取得执行权后必须原子写 `run.execution_started` 并将后台 Run 推进 `running`，再把 `ProjectAgentContinuationCheckpoint.status=running` 持久化为不可重复执行围栏；重放看到未结算的 `running` 必须先恢复已准备的 interaction handoff，否则显式结算为 `outcome_unknown/failed`，不得再次调用模型或工具。普通完成、失败、投递耗尽和新的 Choice/Approval 等待都必须由 `execution-handoff` 在一次事务中写 message、checkpoint、Wait、Run 与事件；续跑中新提交的 Task 进入新的后台 OperationBatch，而不再次悬挂当前 Run。route、客户端、轮询和 refetch 不得成为第二续跑入口。
- **AR-03E — Execution Handoff 唯一写入者。** `ProjectAgentExecutionHandoff` 是不可见、可恢复的交接 intent。Choice/Approval 必须先准备 intent，再由同一模块把 message、ready Session snapshot、Interaction、Run、checkpoint 与 Event 一次结算；OperationBatch 必须在第一个 Task 成员事务中准备 `task_batch` intent、随成员单调增长 Task 集，并在 collecting Wait seal 事务中结算。普通 terminal continuation 也必须由该模块一次结算。旧的前台 `task` suspension/handoff 已删除；adapter 只能结束自己的 Operation Activity，任何 adapter、Choice/Approval helper 或旧 finalizer 都不得结束 continuation Activity、晋升模型历史或另行更新 checkpoint settled。
- **AR-03D — Continuation 投递耗尽必须先结算。** `PROJECT_AGENT_CONTINUE_WAIT` 达到持久 delivery 上限时，Outbox worker 必须先通过唯一 settlement 入口原子结算 checkpoint、Wait、Run、Thread message 与 Session Event，成功后才能把 Outbox 标为 dead。尚未开始执行的命令结算为 `delivery_exhausted`；已进入 `running` checkpoint 的未知结果结算为 `outcome_unknown`。settlement 失败必须保持 Outbox 可重试，禁止留下永久 `awaiting_task` Run/Wait。
- **AR-03A — 失败不自动授权改写，也不改写 Run 结论。** Task 失败事实只属于 Task/Wait/Activity；终态 continuation 必须把成功与失败的真实 Resource/Task refs及 typed error 交给 Assistant。Task 用户可见交付的唯一服务端投影是 Session `taskBatches`：它必须保留尚未 followed 的 Wait 全部成员，并始终展示权威 `errorCode`、服务端 message 和 canonical 本地化原因，不能依靠模型记得解释。Primary 在重新委派前还必须先输出一句用户可见说明，且新请求必须有真实变化。模型说明只是交互增强，不是错误事实 owner。模型可以据此形成一个新的显式重试决定，但必须重新调用正常 Operation；收费重试仍重新生成精确报价并按当前用户设置取得新的显式 Approval 或单次精确 Grant，不能继承失败 Task 的授权。系统不得隐藏自动重试，也不得在没有新 Tool 决定时自动重写、重新提交或写领域事实。若解释/规划回合本身没有协议错误，continuation 可结算为 `completed`，禁止把被解释的 Task 失败提升为 `run.failed`。
- **AR-04 — 用户界面只呈现产品语义。** 普通运行卡片必须从 Session `taskBatches` 按 Wait 投影全部本地化操作名、完整成员和终态进度；分母、分子、失败数、取消数与错误都必须从同一 `tasks` 数组派生，不能再把 `wait.taskIds` 与 active-only 查询拼成两个事实。只有 `terminal=false` 的子集可以驱动画布聚焦与 spinner；终态失败必须留在该批次卡片并由 canonical failure view resolver 展示，直到 Wait 完成原子 follow-up 交接。不得假设只有一个 Operation，也不得展示 taskType、targetType、targetId、operationId、原始工具参数或原始工具结果。`creative_work` 是唯一显式例外：它从普通 `taskBatches` 排除，只由同一 Session View 的 `subagents` 投影，避免一项 Task 同时显示成普通运行卡和 Subagent。Primary 对话中的 Subagent 锚点只显示状态、产物名称、Subagent 标识、委派 goal、生命周期事件计数与详情入口；同一条消息下并行的多个锚点默认折叠成一行汇总，展开才逐项列出。goal 与事件计数是委派意图和进度粗粒度投影，不得替代终态判定；公开推理正文、Skill/工具轨迹明细、终态摘要和完整 strict JSON 仍只属于选中的 Subagent 详情，完整 JSON 默认折叠。切换到 Subagent 详情时，Primary 专属的 Composer、计划、Choice、审批、运行卡和“创作模块”坞必须隐藏；详情只显示所选 Task 的职责与只读过程，不能伪装成可向 Subagent 发消息。Primary 仍允许在后台 `awaiting_task` 时发送新消息；真实 continuation 正在写同一 Thread 时才由权威 Run 投影为不可提交并显示明确整理状态。Subagent 归属由服务端用 Task 的 immutable `origin.runId` 加该 Run 的 `assistantId + scopeRef` 投影成 SessionState.subagents；客户端 Creative Task stream 只接受其中的 taskId，未知 lifecycle 只触发一次 SessionState 刷新，绝不再用 `Task.episodeId` 裁剪或把 `episodeId=null` 当通配。seq 连续时才合并实时 overlay；gap 时删除当前不完整 overlay、只刷新一次并暂停同一 identity，直到新 identity 或终态快照。切换/挂载立即显示完整快照，只对之后新增字符播放动画，不能从 0 回放。产品只可显示 provider 明确公开的 reasoning text/summary；原始或加密 CoT、signature、Skill 正文、系统 Prompt、原始工具参数与内部 metadata 不得进入 UI。
- **AR-04G — Primary reasoning 只有一个流裁判、一个前台活跃指示与一个终态轨迹。** Agents extension 的既有 UI converter 继续唯一投影 message、step、text、tool 与 approval；repo-owned observer 只从同一 `RunStreamEvent` 读取公开 reasoning delta，并写入可唤醒 side channel。`createProjectAgentUiMessageStream` 是两者的唯一输出裁判：先发 converter 的 message `start`，再发 Run 数据与实时 reasoning；SDK 终态 reasoning aggregate 只做逐 block 一致性校验后抑制，缺少实时 delta 时才作为唯一兜底。分叉、缺块或身份冲突必须失败。前台 Run 从提交到权威完成、失败、取消或交出用户决定前必须始终且只显示一个活跃指示：唯一面板尾部指示只消费已统一的 `replyInFlight`，不得再读取 chat transport status、消息内容或某个 part 的局部完成状态来裁决 Run；正在运行且可见的 reasoning 或 Tool 卡只通过同一纯 UI surface contract 临时替代通用三点。空 `reasoning-start`、已完成 reasoning、已输出正文或尚未组装完成的 Tool arguments 都不得被解释为 Run 已结束，也不得制造无反馈空窗。Choice/Approval 只在持久等待事实已经投影时接替活跃指示，后台 Task 由自身生命周期 View 接替，任何 timer、文本内容或局部 part 完成状态都不参与 Run 裁决。运行、Tool use、Approval/Choice/Task 等暂停以及失败/取消期间，reasoning、公开说明与每个 Tool 必须按原 part 顺序独立显示，不能提前出现“调用 N 次工具”或把未结束执行合并。只有最后一条权威 `agent-run.status=completed` 到达后，第一条 Run anchor 才把本轮 reasoning、Tool call 与最后一次 Tool call 之前的公开说明投影成一个已完成 Disclosure；计数只按用户可见 opaque `toolCallId` 去重，内部 `load_tools/update_plan` 不展示也不计数，最终 Tool 之后的正文留在轨迹外。failed/cancelled 不得显示成功汇总。整轮没有公开 reasoning 时不创建汇总，Tool 继续走原 SDK renderer。

  唯一活跃指示的补全：Run 以 `failed/cancelled` 终态结算时，runtime 必须在构建持久 assistant message 前收口全部非终态 part——未取得输出的 tool call 补 `tool-output-error`，未收尾的 reasoning/text block 补对应 end 事件；持久化消息不得含非终态 part，重放历史因此不可能制造永久"运行中"表面。前端 running-surface 注册表是纯 UI surface contract 的唯一实现：注册 key 携带所属消息 identity，只有线程最后一条消息可注册，Provider 只在活跃 turn（`replyInFlight`）统计并在新一轮开始时确定性清空；历史消息的任何 part 状态都不得压制或替代通用三点指示。
- **AR-04H — Resource 链接是结构化交付，不是模型文案。** Operation registry 以 `resourceContract.assistantPresentation` 穷尽声明是否交付本次创建的 Resource；同步成功 outcome 与异步 Task reference continuation 都只能提供精确 `resourceId`。runtime 在最终消息结算前调用 Creative Resource 的唯一 Link View projector，并把结果写为 `data-assistant-resource-links`；该 part 与普通 message 或 continuation checkpoint/Wait/Run 原子结算并随 Thread 刷新重放。模型文字只解释结果，不拥有标题、文件名、href 或资源状态；Markdown renderer 不扫描、补链或改写 `/m/`。前端只显示 Link View 的文件名蓝链，href 可以是受保护媒体路由但不得作为可见文本。
- **AR-04E — Tool 展示身份与结果必须精确。** Tool 卡继续使用 SDK 的一次调用/审批/结果协议；Task-producing Operation 只有在权威 Operation 返回 durable Task receipt 后才显示“已提交”，审批前不得伪造提交成功。`toolCallId` 是 opaque identity，不得从其文本猜测 operation。runtime 必须在 SDK 原始 `tool_called` 事件进入 UI converter 前读取 direct tool name，或用共享 parser 读取 gateway 的非空 `operationId`，登记当前 run 内精确的 `toolCallId → operationId` 关系；完整 envelope、加载资格与业务参数仍由 adapter 校验并以 typed outcome 纠正，执行/审批回调只能幂等复核该关系。审批恢复时 runtime 从已持久化的 Approval member identity 重建同一关系。UI stream 只能用它把 SDK `execute_operation` alias 投影为实际 Operation，或补齐/校验 SDK 传输身份。SDK tool-not-found 虽必须继续给模型字符串纠正文案，但 UI 投影必须从原始 call 与本次实际注册 tools 生成结构化失败，禁止把字符串 output 当作成功。关系缺失、冲突或未注册工具必须显式失败，通用 `call/tool/execute_operation` 不得降级成用户可见的“项目操作”。该关系不执行 Operation、不创建 Task、不参与审批，也不是第二份持久状态。
- **AR-04D — 媒体加载视觉单一。** Assistant 专用 presentation 仍由自己的最终 View 决定 loading、generating、completed 与 failed，不得读取 Canvas lifecycle 或建立状态适配层；图片区域的品牌 Logo、进度环、百分比和 neutral loading background 只能交给全局 `MediaGenerationLoadingView`，不得复制圆环、品牌动画或进度算法。已有输出遮罩、候选解释、Choice、失败原因和领域交互继续由专用 presentation 持有。
- **AR-04 — 工具契约在 registry。** operation 的输入、confirmation、agentFlow、plan/commit 与输出 schema 必须在 registry 统一声明；不得以 operation id 特判或从文案反推控制流。
- **AR-04F — 环境 scope 与 Tool 业务参数分离。** `projectId/userId/episodeId/runId/executionSegmentId` 等可信运行环境只通过 `ProjectAgentOperationContext` 进入 prerequisite 与 executor；送入 Operation input schema 的对象只能包含模型实际提交且 Tool schema 已声明的业务字段。runtime 不得把环境字段注入 strict payload，也不得要求模型重复传当前 scope。需要 episode 的 executor 从 context 读取；缺失时由 prerequisite typed-fail。
- **AR-04A — Operation 调用单入口。** API 与 Assistant Tool 只能把可信来源上下文交给 `invokeProjectAgentOperation`；该入口唯一负责 registry 查找、`channels.api/tool`、prerequisite、输入 schema、direct execute 或 billable Grant invoke、输出 schema 与资源变更提交。同步资源写 Operation 必须使用 invocation-owned transaction，把业务写、输出校验与 Resource Outbox 一次提交。带外部上传的同步写必须显式实现 `prepareTransaction → executeInTransaction → compensateTransactionFailure`：prepare 在事务外完成所有权预检、图片处理/上传与外部分析，只能产生本次唯一且尚未共享的临时 key；短事务必须以 target identity + prepare `updatedAt` 的单条 CAS 重新取得版本写权，再提交领域关系、输出与 Resource Outbox；任意事务、输出或 Outbox 失败都按 prepare identity 补偿，即使 executor 尚无 output。补偿遇到事务结果不明时，必须先按 owner、target identity 与本次 key 查询精确领域关系；关系已存在则不得删除，只有能证明该 key 尚未被本次目标采用时才可清理。任意已有 storageKey 不得由 Operation 充当媒体 GC。Task-producing Operation 的 registry 资源 impact 必须为 `none`；若它在 Task 提交事务内同时预留 pending CreativeResource，可以在该同一事务发布仅表示 pending 已持久化的 Resource Outbox，ready/failed/canceled 通知仍只由 Task Terminal Service 生成。adapter 只翻译 API error 或 ToolResult，不得各自重建执行分流。tool-only operation 经 API、api-only operation 经 Tool 必须在解析或执行前显式拒绝。
- **AR-04C — Operation outcome 穷尽。** `invokeProjectAgentOperation` 与其 Tool adapter 边界必须构造且只返回 `completed`、`noop`、`submitted_tasks`、`wait_choice`、`wait_approval` 或 `failed` 之一。`submitted_tasks` 携带已提交的 `batchId + backgroundRunId + waitId + taskIds` durable receipt，但不是 suspension outcome；`wait_choice` 携带 durable handoff。Tool adapter、stop controller 和 runtime 只能 switch 此 outcome。`effects.longRunning`、`agentFlow.suspendsFor`、Task binding 和 output 字段只能参与 outcome 的构造或契约验证，绝不可由调用方再次从输出形状猜测 lifecycle。旧 `runtime-signal` output parser 与前台 `awaiting_external_task` stop 不得恢复。
- **AR-04B — Tool 写入 authority 必须穷尽。** 每个 Tool-visible 写 Operation 必须恰好属于 `billable plan commit`、`executeInTransaction` 或 `transactional_task_submission` 三种 commit authority 之一；未能证明 Run fence 内原子提交的能力必须保留 API-only。Operation domain 禁止通过 HTTP 调用本应用 route，也不得用 fire-and-forget 或吞错把记录创建与 Task 提交拼成第二执行入口。`create_character` 只事务性创建记录；参考图描述提取是独立文本 Task，参考图生图是独立 `billable_media plan/commit` Operation，两者不得再由 `extractOnly` 在同一 Task type 内切换计费和授权语义。
- **AR-05 — 并发与心跳可证明。** 锁、心跳、超时取消和恢复必须由同一运行时状态协调；旧 run 不得覆盖新 run 的结果。
- **AR-05A — Operation 副作用服从 Run execution fence。** Assistant Tool 调用必须把同一个 abort signal 与 `runId + runVersion + eventSeq` 交给 `invokeProjectAgentOperation`；continuation 还必须携带 `waitId + commandId + claimOwner`。统一入口在执行前拒绝已失效 Run；普通 Task 创建事务、批准计划事务与同步领域写入事务必须在 commit 前锁定 Run 行，并在 continuation 中同时锁定 Wait claim 行后再次校验 fence。同一 execution segment 可以有多个 Tool 成员，但每次数据库提交必须在同一 segment identity 下串行锁定 Run、只接受水位单调前进并确认 Run 仍为 `running`；不能把许可扩展到其他 segment 或终态 Run。心跳、Redis lock 或 continuation claim 失效后，即使 Operation 已经开始，未提交的领域写入也必须整体回滚；只在 execute 返回后检查状态不构成防线。

- **AR-05C — 同一步骤收费调用聚合展示、逐成员冻结。** 一个模型 step 可包含多个收费 Tool call，包括同一个 Operation 的多个调用。runtime 必须把该步骤所有 approval item 作为一张聚合报价卡持久化并只请求用户批准一次，但每个成员仍以 `approvalId + toolCallId + operationId + planSnapshotId` 保存 exact input、不可变 plan 与 quote；operationId 不能充当成员 identity。批准事务为全部成员逐一签发精确 Grant，任一成员不匹配则整组失败；恢复时只允许相同 toolCallId 消费自己的 Grant。拒绝则任何成员都不创建 Task。不得引入 Run 预算、自动批准、跳过确认或由后续模型扩大已批准计划。
- **AR-05B — Execution eligibility 与等待 outcome 分离。** `effects.writes` 只描述领域数据写入，Run 的 `status` 只描述业务正在等待什么；二者都不得裁决一个 execution segment 是否仍能提交。Redis run lock 是当前 segment 的 lease，Run fence 只校验 `runId + runVersion + eventSeq`、abort 与可选 Wait claim，并且只在执行前或写入事务内使用；heartbeat 在持有该 lease 时不得因合法 `awaiting_*` status 撤销 ownership。暂停 settlement 在写自己的 Event 前必须通过 transaction barrier，在 Event 已推进本次 Run fence 后、提交前必须再次检查 abort signal；失锁时整笔交接回滚。`agentFlow.suspendsFor: choice` 只要求当前 invocation 登记完全匹配的不可见 `ChoiceHandoffReceipt`（run、execution segment、operation、toolCall）；最终可见 Interaction/Activity/card 必须由 execution-handoff 与 assistant message 一起提交。通用 invocation 绝不在提交后要求 Run 仍为 `running`、增加 awaiting 白名单或按 operation id 分支。Choice 是 Tool-only、非领域写、无媒体审批的 direct Operation；缺少 durable handoff 的调用必须失败。
- **AR-06 — Run 转换单调。** Run 只使用 `running`、`awaiting_approval`、`awaiting_choice`、`awaiting_task`、`completed`、`failed`、`cancelled` 七种状态。状态转换必须经事件 reducer 校验合法前驱并执行 CAS；三个终态不可重开。`run.failed` 只能从非终态写入 primary error；终态后到达的 `run.failed` 只作为已经持久化的 `ProjectAgentEvent` secondary diagnostic，绝不可覆盖 primary error 或重开 Activity/Wait。失去 Redis lease 所有权必须中止模型流并进入 `cancelled/run_lock_lost`，不得继续写入或伪装成业务失败。
- **AR-06A — Interaction 与 Activity 单调。** Approval 和 Choice 创建都必须通过同一个事务 authority，在持有目标 Run 行锁时一次性读取并 supersede 旧 pending interruption、结算其 Activity、完成前序 Activity 并 raise 新 interruption；任一 Event/reducer 写入失败必须整体回滚，禁止先 supersede 后 raise 的两阶段窗口。`activity.started` 只能 create，重复 identity 必须 conflict；`completed/failed/cancelled` 必须从 open 状态执行恰好一行的 CAS，零行或多行都原地失败，禁止终态重开或错误 activityId 静默前进。
- **AR-07 — Session/UI 只投影持久协议。** Panel 不得扫描历史 message、tool output 或 `task-submitted` part 推断 Task、资源刷新、operation source 或当前决定；这些 identity 必须由 Session `currentActivity/taskBatches/pendingInteraction/subagents` 和正式 SSE Resource envelope 提供。Creative Subagent 只由同 scope 的 `creative_work` Task、Task.status/result 与有界 lifecycle projection 派生；通用 Choice 只由持久 Interruption Offer 投影，不存在风格、剧本、资产等专用 Choice renderer 或运行卡。Session projector 必须把当前前台 Run 与后台 Task Run 分开；后续水位、去重、刷新与断线规则继续由本模块的持久 Event/Outbox 契约裁决，timer、轮询、文案和 DOM 均无状态解释权。
- **AR-07A — Thread clear 是带水位的 scope 事实。** 清空 Thread 必须在持有 project scope lock 的同一事务删除消息、追加唯一 `thread.cleared` scope Event 并写 Session broadcast Outbox。Session/Thread GET 必须返回持久水位；客户端只接受不低于已见水位的响应。权威空 Thread 必须 replace；清空后重建的非空 Thread 若持久 `thread.id` 与客户端最近接受的 identity 不同也必须 replace，只有同一 Thread identity 的快照才可与未持久 optimistic message 合并。

- **AR-07B — Subagent live stream 是 Task View 的瞬时输入，不是第二状态源。** 同一 Task attempt 的公开 reasoning 与未完成 structured output text 共用 Task stream `streamRunId + stepId + stepAttempt + lane + seq`，但由 `lane` 与 stream kind 严格隔离；resolver 只在 seq 连续时合并，reasoning 与 durable block snapshot 做前缀一致性校验，gap 时立即丢弃该瞬时段并重读 Session，分叉显式失败。Primary 与 Creative Worker 共用的 public reasoning normalizer 也是模型 `reasoning → text/tool input` 输出边界的唯一解释者；前台 Run 可直接发送 delta，后台 Task adapter 可以合并传输，但必须在该共享边界发布不足一个分块的尾部，并把当前完整 block snapshot 投影回同一 lifecycle。运行中详情可逐 delta 展示未校验 JSON 文本；它不能进入 Resource、checkpoint 或 Primary 上下文，也不能被解析为完成。Task lifecycle SSE 仍只触发最终 View 刷新；终态事件之后必须发起一份不复用旧 in-flight 请求的新 Session 读取，并证明返回 View 中同一个 `taskId` 已终态，才能清除 stream overlay。经过 strict schema 校验的 `Task.result` 与 `lifecycleProjection` 是终态 View，Task.status 是唯一终态，stream 不得完成、失败或重试 Subagent。

## 部署边界

`ProjectAgentExecutionHandoff(kind=task)` 与前台 `awaiting_external_task` 已一次性切换为 `task_batch + collecting Wait + 独立后台 Run`，Approval payload 也已切换为精确 member 列表；不提供双 parser 或兼容 writer。固定 SDK Tool 前缀使用 registry 声明的 direct 基线加 on-demand gateway；gateway 一次性切换为只含必填 `operationId + argumentsJson` 的协议，序列化 RunState 不读取旧 `kind/contractId` envelope。部署前必须排空旧版本仍处于 `running/awaiting_task/awaiting_approval/awaiting_choice` 的 Assistant Run、Wait 与 Interruption，再切换所有应用和 worker 实例。不得让旧 worker 消费新 `task.collection_*` Event，也不得让新 runtime 恢复旧单 Task handoff、旧 gateway envelope 或旧 Approval。

`tests/integration/task/project-agent-continuation-settlement-concurrency.integration.test.ts` 以真实 MySQL 并发两个 claim owner，证明同一 resolved Wait 只授予一个执行者。合法删除 Run 时外键将 `Wait.runId` 置空，后续 claim 必须按 stale/permanent delivery 终止；不得为绕过外键的损坏数据增加运行时 fallback，损坏数据属于完整性告警与运维修复。

## Operation execution fence 状态所有权

| 事实 | 唯一所有者 / 写入者 | 消费者 |
|---|---|---|
| 当前 Assistant 执行资格 | `ProjectAgentRun.status + runVersion + eventSeq` / Event reducer | Operation execution fence |
| 当前进程已观察到的失锁事实 | Runtime `AbortController` / heartbeat、Redis lock 与 continuation claim 续租器 | 模型 stream、Operation invocation、commit barrier |
| Operation 最终提交资格 | `assertProjectAgentOperationExecutionFenceInTransaction` 对 Run 行及可选 continuation Wait claim 行加锁后的联合裁决 | Task 创建事务、批准计划事务、transactional direct executor |

写入者变化：Operation 过去只在 Activity Event 写入时使用 Run fence，领域 execute 已经开始后仍可绕过。现在 Tool adapter 不再丢弃 signal/fence；同步领域写入由 invocation-owned transaction 执行，Task 与批准计划在各自权威事务末尾调用同一个 barrier。API 调用不伪造 Assistant fence，仍按其自身鉴权与幂等契约执行。

写入者变化：删除 scope 扫描、resolved Wait 列表/claim helpers 和客户端 follow-up 控制入口；续跑调用者收敛为 Outbox worker 一个。模型输出不再先于持久 checkpoint 直接宣告 Wait/Run 已结算；checkpoint 重放只完成第二阶段，不再次调用模型。

## 历史回归

- 图片附件首版只为后续媒体生成设计：消息给 Primary 的内容只有 `<uploaded_media ... resourceId>`，`get_resource` 又有意只返回安全元数据，因此真实 PNG 即使清晰可读，模型也从未收到像素；它随后错误委派 screenplay Worker，Worker同样只能看到元数据并创建“待识别剧本”Resource。文本来源捕获防线只覆盖 `userTurnText`，没有覆盖上传图片这一新实例。当前附件仍以一个 Resource identity 持久化，但图片在每次模型请求前经唯一 model-input filter 和既有 outbound-image owner 投影为真实 `input_image`，SDK Session 写入时恢复稳定 marker；音频未接入模型本体时继续明确保持 metadata-only，不做自动降级或伪装。
- 图片本体接入后首次把 server-only `model-input.ts` 从客户端已使用的 `media-attachments/index.ts` barrel 重新导出；Turbopack 因此沿 `outbound-image → media service → storage → sharp → detect-libc` 把 Node `child_process` 带进 Client Component graph，首页构建直接失败。第一次修复删除 barrel re-export，并把同一个混合模块标记为 `server-only`；但 Task Terminal 会经 `model-session.ts` 读取其中的纯 marker canonicalizer，Outbox Worker 也会经 `server-follow-up.ts → runtime.ts` 读取图片解析，独立 `tsx` 不经过 Next alias，因而在注册任何 BullMQ Worker 前以 `MODULE_NOT_FOUND` 崩溃。`tsx watch` 外壳继续存活，所有 Task 只停在 `queued/waiting`；Next build、TypeScript、ESLint、Logic 与 Operation conformance 都没有执行独立 Worker entry，旧的临时启动 smoke 又没有在后续图片边界提交中重跑，所以防线再次漏过真实路径。当前客户端 barrel 仍只保留浏览器安全能力；`model-input-protocol.ts` 唯一拥有纯 marker 协议，`model-input-runtime.ts` 独占数据库读取与图片出站并明确同时服务 Next 命令和 Outbox continuation，整个 Worker 可达图不再加载 Next 专用 marker。适用验证必须同时包含 Next production build与隔离的完整 Worker entry 启动；`tsx watch` 对未来入口崩溃仍不会退出，是尚未收敛的开发态进程监督盲区。

- 动态视频 Schema 曾为了在模型调用前拒绝“音频无图片”和“音频搭配首尾帧”而保留两个共享 `request.kind=new` 的结构分支；strict projector 又把可选字段暴露为 nullable。旧 null normalizer 只按 `const` 选择联合分支，因此两个分支同时命中时无法判断哪些 null 应删除，最终把模型按公开 Schema 提交的 `contextReferences=null`、`audioReferences=null`、`resolution=null` 原样交给 canonical runtime 并退化为 `OPERATION_INPUT_INVALID`。旧 conformance 分别验证动态 Schema 和 runtime parser，却没有证明模型表面与 canonical parser 同源。当前动态 Schema 已删除：canonical `create_video.kind=new` 是唯一产品输入对象，strict JSON Schema 只由它投影，音频依赖、模型能力与引用上限由唯一 planner 在收费提交前裁决。已删除的动态配对测试不再作为旧语义防线；生产 registry conformance 只验证现存的单一 Schema 权威。
- 上述 null normalizer（d3317052b）修复后同一不变量第三次换形式复发：动态 Schema 把项目比例投影成 `aspectRatio` const，normalizer 把任何带 const 的属性当判别器，模型合法提交的 `aspectRatio=null` 直接否决分支；required-key 判据又拿 strict 化全量 required 去匹配另一份 runtime Schema，令兜底永远选不中分支；审批恢复还用不同 Schema 重新归一化原始输入，把已批准执行打成 `OPERATION_INPUT_INVALID`。旧 conformance 混配两份 Schema，测不到生产配对。当前不再维护配对：registry canonical runtime schema 是唯一 writer，strict tool Schema 只由它确定性投影；planner 独占配置/capability 校验与服务端字段注入；审批恢复直接执行 PlanSnapshot 的 `normalizedInput`。因此不存在动态/静态方言、配对或恢复时切换 Schema 的路径。
- `b15984af0` 将完整 Agents SDK Session 历史接入 versioned pending snapshot 后，成功 settlement 与 stale `running` Run 取消已经分别具备 exact commit/discard，但普通 stream error/cancel 仍调用 `buildCommit()` 强制把当前 snapshot 标记 ready，continuation `outcome_unknown` 又只结算 message/checkpoint/Wait/Run 而不处理 pending。真实 OpenRouter TLS 握手中断因此先让 continuation 进入 outcome unknown，再把同 Thread 的所有新 user turn 以 `PROJECT_ASSISTANT_PENDING_MODEL_HISTORY_CONFLICT` 永久拒绝；已有 continuation 集成场景只断言 Run、Wait、Checkpoint 与 UI message，没有创建 pending snapshot或启动下一 execution segment，因而未反证该组合。当前防线把 terminal model-history disposition 收敛为显式 `commit | discard`：Run settlement 必须选择其一，Choice/Approval 与成功 continuation 必须携带 exact ready commit，网络错误、取消和未知 continuation 只按持久 execution identity 原子 discard；冲突 guard 保持 fail closed，不增加 user-turn fallback 或自动重放。真实 MySQL Critical 场景同时证明 committed version 不变、下一 segment 可写、重复/并发终态不误删其他 segment。真实 Provider TLS 故障仍由受控 provider seam 复验，不依赖公网偶发失败。

- Assistant 上下文治理曾连续两次以同一根因复发。初版把「模型看到什么」拆给三个互不知情的解释者：`message-compression` 用写死的 `MAX_ESTIMATED_TOKENS=12000` 只统计聊天文本、`toAgentInputItems` 只发出 user/assistant 文本、approval 恢复则直接还原 RunState；摘要还被构造成会被 converter 静默丢弃的 system UIMessage。Agents SDK 迁移时虽然为单次 outgoing payload 加上 `callModelInputFilter`，跨 turn 仍由另一个手写转换器从 `messagesJson` 只取 `part.type === "text"`，于是 reasoning、`dynamic-tool`、Tool arguments/results 和所有 data part 在下一轮全部消失。通用 Choice 又用空 `{}` 合成 `function_call`，模型收到用户选择后无法再看到自己写过的三个方案；旧防线只约束“本次发出什么”，没有覆盖“下一 turn 从哪里取历史”，所以真实路径继续漏失。

  当前防线删除 UIMessage→AgentInputItem 重建、隐藏 follow-up 消息与空 Tool call 合成三条旧路径；跨 turn 只读写 Agents SDK Session 的完整 `AgentInputItem[]`，Choice handoff 额外冻结完整模型参数。随后完整产品复验暴露上一 execution segment 的动态 `load_tools` contract 会被模型复用；第一版防线把所有 on-demand Operation 都签成随机 contract，再按 callId 删除上一 segment 的全部 load call/result，静态工具因此也反复失去已经读过的 Schema 并触发 `NOT_LOADED/CONTRACT_UNKNOWN`。同一时期独立 48K/24K summary 在统一 200K+ 模型预算前触发，Prompt 又要求旧 summary 每项原样追加，导致 checkpoint 单调增长并在 Task follow-up 前同步阻塞 6 分 48 秒。当前删除全部 discovery contract 与 execution-scope 过滤；`load_tools` 历史只包含 registry canonical Schema 知识，不再携带会过期的执行身份。上下文删除 48K/24K 与 append-only summary，只在唯一预算经 Tool result shedding 后仍超限时调用一次 bounded `context_compress`，向 canonical Session 追加替换性 checkpoint并保留全部原始 items。真实 provider cache 命中与 checkpoint 召回质量仍需发布后用 `assistant.run.summary` 的 per-request `inputTokens` 复验。
