# Creative Skill 与无状态 Worker

## 设计理念

主 Agent 负责读取项目事实、规划、委派、调用完整 Operation registry 和与用户沟通；专业创作推理由后台 Creative Subagent 承担。每个 Subagent 由一个 `creative_work` Task 承载，但 Task 只提供持久生命周期、结果保存和恢复，真正的 Creative Worker 仍是一次性、无状态、无业务写权的模型循环。

Worker 启动时只收到 output registry 为本次 output kind 绑定的一个专业 Creative Skill 目录项，并只读加载该 Skill。Skill 是专业知识，不是工具权限、工作流、项目事实或第二套运行时。采用单层单文档 Skill：每个 identity 只有一份 `SKILL.md`；当前知识量不足以证明需要固定专业角色、`references/`、Discover 阶段或递归知识树。

## 不变量

- **CS-01 — Skill registry 是唯一身份入口。** Skill id、版本、标题、摘要、标签与 `skill://` URI 只由 `CREATIVE_SKILL_REGISTRY` 声明；registry 不声明未被投影给 Worker 的字段（`keywords` 已删除）。发现、URI 解析与读取必须经过该 registry，禁止从 Operation 名、目录遍历、模型猜测或任意文件路径推断 Skill。
- **CS-02 — Skill 保持单层、单文档且职责分离。** 每个已注册 Skill 只有同目录下唯一的 `SKILL.md`，不按语言分叉；不建立 `references/`、固定专业角色或递归知识树。Skill 是给模型读的专业知识，不是用户可见内容，因此不受 i18n 硬约束；Worker system prompt 是单份英文模型侧文本，输出语言由 creative-core 与各 Skill 的内容语言条款决定（`score.generationPrompt` 按音乐模型能力固定英文）。真正随语言变化的只有交付物本身——最终视频提示词必须与内容语言一致，因此完整提示词示例在同一份文档内并列给出中英两套，而不是分成两份文档。自动预加载的 `creative-core` 独占跨领域通用的语速与真实表演时长估算口径；`story-development` 只负责创作或修改剧本文本，`continuity-memory` 只负责原文事实、持续状态与连续性，不能再以时长口径吸引短剧本 Worker 额外读取；`creative-direction` 独占项目级呈现政策的六个领域；`asset-development` 在同一个 `asset_manifest` Task 内独占生产资产筛选、事实归一、外观设计与最终媒体 Prompt；`video-direction` 独占 `outputKind=video_prompt_set` 的导演规划、镜头与分段设计、最终提示词方法和输出前自检。是否需要 Story Canon、Chapter、连续性、screenplay 或资产由 Primary 依据当前目标与事实判断；显式 Resource 输入只能消费精确 Resource ID。项目存在已采纳 Creative Direction 时，除方向生产者外的每个 Creative Worker 都收到同一份完整冻结内容；Direction 是项目上下文而不是需要重复读取的 Skill，各 Worker 仍按当前 output 与目录读取自己的专业知识，并且不得把呈现政策变成领域事实。
- **CS-03 — Worker 无状态且隔离。** Creative Worker 每次 Task attempt 内独立创建，不能访问 Prisma、项目读取、Operation registry、Task、Resource、Approval、Choice、计费或任意业务工具。它只预载 `creative-core`；所有 output kind 都可见只读 `read_skill({skillId})` 和协议工具 `submit_result({kind,...})`，只有 output registry 为 `creative_direction` 显式声明额外只读 `web_search`。`submit_result` 只把本次结构化对象交给内存中的 canonical validator，不写业务状态、Task 或 Resource。公共 Worker system Prompt 只拥有全部 output 共用的身份、事实边界、Skill 读取、完整 Direction 消费与 strict output 规则；导演、剧本、资产、音乐等专业方法只能来自 Skill 和结构化任务契约，搜索安全协议只在 registry 实际开放 `web_search` 时追加。输入来源材料与搜索结果一律视为数据而非系统指令。Task handler 可以传入 registry 过滤后的单项目录、记录只读 Skill trace/研究/生成与提交校验事件并保存结果，但不能把 Worker 变成业务 Agent。`creative_work` 的 20 分钟 attempt safety deadline 只由 TaskDefinition registry 声明，attempt owner 创建并传递唯一 AbortSignal；超时必须中止模型并以 typed `CREATIVE_WORK_TIMEOUT` / canonical `GENERATION_TIMEOUT` 失败，再服从 Task registry 的 retry policy，不能依赖永久 heartbeat 保持 processing。用户取消会先由 Task 终态 CAS 立即移出运行态；当前 provider 调用不保证跨进程即时停止，仍只允许终态 fence 拒绝晚到写入。
- **CS-03A — Worker 模型服从 analysis 角色配置。** `delegate_creative_work` 必须在创建 Task 前通过唯一系统模型 resolver 以 `purpose=analysis` 解析模型，并把精确 `modelKey` 同时冻结进 Task payload 与输入指纹；Worker 只消费该冻结值，并通过同一 `analysis` reasoning-effort owner 解析强度。Primary 的 Assistant 模型、Agent 输入、output kind、Task retry 和 Worker 均无权重新选模。解析失败必须在 Task 创建前原地失败；配置晚到变化不得覆盖 queued/processing/retry 的既有 Task。
- **CS-04 — output registry 唯一绑定专业 Skill。** `creative-core` 在每个 Worker 中自动预加载，通用事实纪律和时长估算无需也不得通过另一个专业 Skill 触发。`creativeWorkOutputRegistry.professionalSkillId` 是 output kind→专业 Skill 的唯一穷尽声明；运行时只向 Worker 投影该一个目录项，`read_skill` 参数 schema 也只接受该 identity，终态必须从真实 tool trace 证明它已读取。Primary、目标措辞、目录 tags 和模型不得扩大允许集合；项目 canon、系列设定、已采纳 Direction 与其他复用事实来自冻结 Context/Resource，不靠伴读 `continuity-memory` 补充。当前映射为：`screenplay/chapter_plan→story-development`、`story_canon/continuity_analysis→continuity-memory`、`creative_direction→creative-direction`、`asset_manifest→asset-development`、`video_prompt_set→video-direction`、`music_direction→music-direction`。Skill 正文与读取代码在同一仓库评审，其体积是撰写约束而不是运行期风险；`skillContentChars` 只是可观测指标。
- **CS-05 — 主 Agent 委派入口与生命周期唯一。** `delegate_creative_work` 是主 Agent 获取专业创作推理的唯一 Operation；它接受单个请求或批量请求，并通过既有 Task submitter 为每个逻辑请求创建一个 `creative_work` Task。一个 Subagent 恒等于一个 Task，`Task.id` 是唯一 Subagent identity，`Task.status` 是唯一生命周期事实。禁止恢复同步 Tool 内运行 Worker、`ProjectAgentActivity.id` 充当 Subagent identity、`subagent.progressed` 事件 writer 或第二套 Subagent 状态机。
- **CS-06 — 输出契约穷尽。** Worker output kind 与 strict schema 只由 `creativeWorkOutputRegistry` 声明。当前集合为 `screenplay`、`story_canon`、`chapter_plan`、`continuity_analysis`、`creative_direction`、`asset_manifest`、`video_prompt_set` 与 `music_direction`（`creative_review` 能力已于 2026-07 按产品决策整体删除，历史 Task 与 Resource 仅按事实展示，不保留第二解析路径）。`screenplay` 只物化文本与写作元信息，不含生产资产 registry、scene ranges 或数据库 identity；用户原文直接保存不以 Worker Task 为前置。`asset_manifest` 只强制精确引用一个 screenplay Resource；是否存在 adopted Creative Direction 不构成门槛。Worker 一次完成筛选、设计和 Prompt；精确 screenplay Resource 与 Lineage 记录实际输入，服务端只编译稳定 `manifestAssetId` 并拒绝名称/别名歧义，不要求模型回传 excerpt、offset 或逐项来源证明。每个 asset 只保留真实有消费者的字段：`stableDescription` 写入资产身份，`generationPrompt` 由 `create_image.request.kind=manifest_assets` 从 adopted manifest Resource 服务端直读执行（CR-21），Primary 不复制；禁止恢复 `sourceRefs`、`negativePrompt`、`referenceRequirements`、`continuityRequirements` 等无人消费或伪装确定性证明的平行字段。`music_direction` 的 strict 输出以必填可空 `score` 承载唯一最终配乐执行指令：非空 `score.generationPrompt` 由 `create_audio.request.kind=music_direction` 服务端直读执行（CR-22），null 表示刻意不配乐；cue 时间线只是解释性投影，不再被任何模型二次消费。没有实体通过全部生产门槛时允许显式空 `assets` 并说明原因。每个 `creative_direction` Task 只返回并物化一份包含 `styleSummary/rawUserStyle` 与 `visual/narrative/directing/editing/sound/assetPolicy` 的完整最终项目政策；Worker 在内部完成方向取舍，strict schema 不表达候选集合、候选 identity 或多版本模式。规则与禁止项写入所属领域，不建立全局 `invariants/avoid`。只有显式 `adopt_creative_direction` 才写 `project.creative_direction` Binding，默认不生成预览图。未知、缺失、错 kind 或超预算输出必须原地失败。
- **CS-06D — Creative Direction 只由服务端统一完整注入。** `creativeWorkOutputRegistry.injectCreativeDirection` 是 output kind→是否注入的唯一穷尽声明：除 `creative_direction` 生产者为 `false` 外，`screenplay`、`story_canon`、`chapter_plan`、`continuity_analysis`、`asset_manifest`、`video_prompt_set` 与 `music_direction` 全部为 `true`。`delegate_creative_work` 在创建一批 Task 前只读取一次当前 `adopted_creative_direction` Binding，校验精确 Resource/owner/scope/content 后，把同一份完整 `creativeDirectionSchema` 内容与 resourceId 冻结进每个非生产者 Task；运行中 Task 不受后续换绑影响，新 Task 自动使用新 Resource。六领域正文是权威呈现政策，`styleSummary/rawUserStyle` 只提供摘要和原始意图语境，不能覆盖正文。没有 Binding 时统一注入 `null`，任何 output 都不得因此失败。Primary 对非 `creative_direction` 请求显式引用 Direction Resource 必须原地失败；Chapter compiler 与 Asset Manifest 不得保留手动传 Direction、核对当前 Binding、conditional style resource 或各自裁剪领域的旁路。Worker 自行判断与当前专业任务实质相关的内容，但不能访问 Project、主动重读 Binding 或读取其他专业 Skill。
- **CS-06E — 方向研究能力、提示与证据由运行时共同裁决。** `creativeWorkOutputRegistry.workerTools` 是 output kind→额外 Worker Tool 的唯一穷尽声明，当前只有 `creative_direction=['web_search']`，其他 output kind 为空。运行时从同一声明同时决定是否创建研究状态、是否暴露 Tool、是否向公共 Prompt 追加搜索协议；没有该能力的 Worker 不看到 Tool，也不看到搜索说明。搜索是条件式能力：只有任务依赖最新、陌生、冷门、地域性、平台性、社群定义、含义不明或 Worker 无法高置信度解释的信息且现有输入不足时才调用；零调用是正常完成。每个方向 Task 用冻结的 `maxWebSearchCalls` 限制对统一 OpenAI hosted research service 的外层调用，服务内部可自主规划多条托管 query。运行时根据真实 Tool 结果构造 `research`，只保存 outer brief、hosted queries、状态和 citation title+URL；综合报告与 image 证据只作为本轮 Tool data。搜索触发除条件式判断外还有一条不依赖模型主观置信度的强制条件：用户原话中的专名若无法当场给出可执行外观或机制，必须搜索；首份报告若在会改变六领域政策的点上仍有缺口，必须在剩余预算内针对该缺口补搜。返回图片是外部证据，Worker 只能使用报告中明确陈述的视觉观察，不得把任何外部图片当作项目资产或参考图。`not_attempted` 不产生 warning，只有真实尝试后的不可用、失败、部分完成或预算耗尽才确定性补入 warning。模型不得自报来源或把 report/citation 写入 Direction structured content；Task result 与 Direction Resource 的 generation metadata 是证据存档，六领域正文仍是唯一创作政策。
- **CS-06C — 完整契约作为数据，根对象 Tool 负责同轮提交。** `creativeWorkOutputRegistry` 的 Zod schema 是唯一业务校验权威；每个 Worker attempt 从它确定性生成两种同源投影：完整 canonical JSON Schema 作为模型输入数据，保留长度、范围、pattern、array-count、联合与严格字段规则；Provider Tool 参数则以同一结果对象为根，只删除已知不兼容的约束关键字。模型直接调用 `submit_result({kind,...})`，不得增加 `output`/`outputJson` envelope，也不得手工构造第二层 JSON 字符串。Tool 在同一 attempt 内用原始 Zod schema和冻结上下文校验：失败正常返回 `accepted=false +` 有界字段 path/code/message，允许模型在同一 Run 修正；成功才令 Agents loop 终止。Provider transport sanitizer 不拥有业务合法性，不得自动修补、按 provider/model 分支、恢复动态 `outputType` 或发起另一次模型 repair。
- **CS-06B — 来源内容由服务端重读。** Creative request 对 Resource 来源只接受 `resourceId`；提交 Task 前由服务端重新读取 Resource 的真实内容、schema、owner 与 scope，并以该内容替换调用方材料。Worker 不接收调用方伪造的 Resource 文本，fingerprint、名称、最近记录或“最新”描述都不是输入身份。Domain provenance 可以携带用户提供/导入等来源说明，但不能冒充 Resource 事实。
- **CS-06A — 导演知识内化进唯一视频 Prompt，引用直接使用 Resource ID。** `video_prompt_set` 的 strict 结果只表达执行真正消费的 `kind` 与 `segments`；每个 segment 只含稳定 `key`、允许的整数 `durationSeconds`、唯一创意指令 `prompt` 和 `mediaResourceIds`。这些 ID 必须来自 Worker 收到的精确 source materials；Primary 只提交 Prompt Set Resource ID，服务端从 Prompt Set 的持久 Lineage 验证图片/声音 ID 并按各自顺序构造 `@ImageN` 与 `@AudioN`，不得让 Primary 重新映射、猜测或复制。Primary 只允许传整部/本章总时长，严禁预先指定段数或逐段时长；服务端从固定视频能力注入允许时长、最小/最大时长、参考图片与参考音频数量上限以及项目画幅，这些上限与 `create_video` 校验的是同一份 capability 事实。Worker 按目录说明读取 `video-direction`，把镜头、表演、动作、机位、构图、视线、剪辑点、连续性、逐字对白、绑定音色、同步声音与条件式转场全部内化进每段 `prompt`。`@ImageN`/`@AudioN` 只是执行层槽位契约名，不出现在提示词文本里；`prompt` 中素材以内容语言的顺序编号提及指代（中文 `@图片N`/`@音频N`，英文 `@Image N`/`@Audio N`，即 Seedance 生态的原生记法），编号与槽位顺序一一对应，不写“图片1（@Image1）”式双重记法。相邻镜头与片段必须形成真实景别变化和严格时间递进；快切组必须留在同一 segment。运行时验证 key、总时长、segment 时长、媒体 ID 唯一性与冻结能力；画幅和原生音频由执行层持有。禁止恢复自然语言 reference key、`globalDirection`、`directorTimeline`、`finalPrompt`、`audioIntent` 或隐藏串行 Task。
- **CS-07 — Task 是唯一持久容器，Worker 不获得写权。** 完整 strict 结果与 Skill trace 只保存于 `Task.result`；Task payload 中只保存请求、冻结模型、输入指纹、来源身份和有界 lifecycle projection。公开 reasoning 以 block snapshot（最多 64,000 字符并显式 `truncated`）更新同一 projection；没有公开 reasoning 时，模型 response start/done 只产生不含思维内容的 `generation` 阶段事实。`read_skill`、研究和 `submit_result` 的 started/terminal 生命周期也进入同一 projection；拒绝事件保存字符数、输入 JSON 类型、顶层字段总数/至多 64 个字段名和至多 64 条 path/code/message，不保存字段值、失败候选正文、Tool 原始参数、系统 Prompt、Skill 正文或私有/加密 CoT。reasoning token delta 与普通模型 `output_text_delta` 只复用 Task stream 做瞬时展示，不写 lifecycle projection、Task result 或领域状态。只有同一 attempt 内成功通过 canonical schema 与冻结上下文校验的内存结果，才可在模型 loop 完成后提交 Task result。Task created/progress/terminal Event 与 Assistant continuation 只能使用 TaskDefinition 声明的 reference projection，禁止复制长剧本、Story Canon、章节上下文或完整 Worker JSON 进入 SSE、Session、Wait 或模型续跑上下文。主 Agent 通过正式 `get_task(taskId)` 读取完整结果；用户选择 Subagent 详情时由同 scope 鉴权 reader 按 taskId 读取同一 `Task.result`，两者都不形成第二 writer。持久 trace 与 lifecycle projection 中的 `skillId` 和 `outputKind` 是历史事实，按有界字符串解析，不与当前 registry 枚举耦合；registry 成员校验只发生在 `read_skill` 工具边界与请求创建时，UI 对已从 registry 删除的历史身份回退显示原始 id，不得因 registry 演化拒绝解析既有记录。
- **CS-08 — 批量只复用既有聚合协议。** `delegate_creative_work` 只有一个 `delegation` 联合：`source=requests` 一次提交一个或多个调用方已备齐上下文的请求，`source=chapters` 由服务端 Context Compiler 直接把每个持久 Chapter 的最小上下文写入对应 Task。一个请求或 Chapter 对应一个 Task。成员只通过现有 `OperationBatch + collecting Wait` 聚合，全部终态后只由现有 Outbox continuation 恢复主 Agent 一次。禁止 nullable 空分支、另建 Subagent Batch 表、每 Task 一个 Wait、首个 Task 完成即恢复、前台阻塞或按结果顺序串行。
- **CS-09 — Subagent UI 只按 origin Run 投影 Task。** SessionState 先按当前 `assistantId + scopeRef` 读取权威 Assistant Runs，再只接收属于 `SessionState.subagents` 权威 taskId 集且声明 canonical `creative_work_v13` protocol 的 `creative_work` Task，以 `Task.status` 与 lifecycle projection 构造运行中和终态 View；未知 lifecycle 最多触发一次 SessionState 刷新，服务端 origin Run projector 决定是否纳入。Task 的 `episodeId` 只表达输出 Resource scope，不能用来裁剪 Subagent UI；因此 Episode Run 发起的项目级 screenplay/creative-direction Task 仍属于该 Run 的 Subagent。同一 Task 不能同时显示为普通运行卡与 Subagent。Primary 消息锚点只提供 status、output kind、Subagent 标识和详情入口，不内联 reasoning、Tool 或结果；选中详情默认展开按事件顺序投影的公开 reasoning、真实 generation 阶段、Skill、研究与提交校验轨迹，终态 summary 保持可读，完整 `Task.result` JSON 由同 scope reader 读取并默认折叠。刷新读取 durable snapshot，实时 reasoning 只作为带 identity/seq 的 overlay；seq gap 时只刷新一次、删除不完整 overlay 并抑制该 reasoning identity 的后续 delta，直到新 identity 或终态快照。挂载或切换先立即显示完整 canonical 快照，只有之后新增字符播放动画。没有 Provider 公开 reasoning 时只显示真实阶段，不生成或猜测思维链。拒绝详情必须显示服务端记录的参数类型、长度与顶层字段名，不能根据 validation message 猜测模型提交形状。历史 message、Tool 卡、文案和 DOM 不得反向推断状态。部署前必须排空 v12 queued/processing Task 与 Wait；不提供 v12/v13 双 parser。
- **CS-10 — Story Canon、Chapter 与连续性是独立能力。** `story_canon`、`continuity_analysis` 与 Chapter 计划分别是可独立请求、独立采用、独立生成的事实；采用 Story Canon 不创建 Chapter，创建 Chapter 不自动委派 Worker，任何 Task 终态都只恢复 Primary。`compileCreativeChapterContext` 只在 Primary 显式以 Chapters 并行委派时，为一个 Chapter 从精确剧本/Story Canon/Chapter/asset Resources 纯派生最小上下文；它不写事实、不创建 Task、不决定顺序，也不接收 Creative Direction。系统不持久化 WorkerGroup。
- **CS-11 — 创意判断只有 Skill + Creative Worker。** Operation registry、Task/Wait、Approval、通用 Choice、Resource、Canvas、计费、Run fence、provider adapter 与确定性执行 builder 保留；旧 script intake、剧本/Story Canon/风格/Chapter/shot/资产/BGM 专业 LLM writer 与固定卡片必须删除。同一种判断不得同时保留旧 Prompt writer，Worker 结果也不得再经过另一个 LLM 重写。
- **CS-12 — Operation 合法性没有剧本与方向前后置门槛。** `creative_direction` 不要求已有剧本，`screenplay` 也不要求已有 Direction；Primary 可以按用户目标先生成任意一方。若项目已采纳 Direction，新 screenplay Task 会自动获得完整方向并自行使用相关内容，否则照常工作。正式 `asset_manifest` 只强制精确 screenplay，方向不存在时也必须可执行；任何一方都不得自动生成、自动采用或启动下一步。Primary Prompt 对 `>15s` 完整视频规定的 Direction/资产先行只是一条产品规划纪律，不得下沉为 Worker、Task、Operation 或服务端 eligibility，也不改变上述合法输入。

## 权威入口

- Skill identity、目录与读取：`src/lib/creative-skills/registry.ts`、`uri.ts`、`loader.ts`。
- 单层 Skill 内容：`src/lib/creative-skills/skills/*/SKILL.md`（每个 identity 唯一一份）；剧本创作、风格与资产分别由 `story-development`、`creative-direction`、`asset-development` 独占。
- Worker 输出与运行边界：`src/lib/creative-worker/output-registry.ts`、`runtime.ts`、`tools.ts`、`skill-access.ts`。
- 委派、Resource 来源回读、Task payload/result 与幂等输入：`src/lib/operations/domains/assistant/creative-ops.ts`、`src/lib/creative-worker/task-contract.ts`；模型角色唯一解析：`src/lib/model-access/system-model-resolver.ts`、`src/lib/ai-exec/reasoning-effort.ts`。
- Creative Direction 终态物化与采用：`src/lib/creative-resource/creative-work-materialization.ts` 为每个成功 Task 物化恰好一个不可变 `project.creative_direction` Resource；`src/lib/operations/domains/assistant/creative-direction-ops.ts` 只验证 completed Task provenance 并更新精确 adopted Binding。
- Screenplay 与 Asset Manifest 严格契约、manifest identity/来源证据校验：`src/lib/screenplay/**`；两者终态仍只由 `src/lib/creative-resource/creative-work-materialization.ts` 物化。
- Task 执行：`src/lib/workers/handlers/creative-work.ts`；它调用无状态 `runCreativeWorker`，不能写领域事实。
- Task reference projection：`src/lib/task/definition.ts`、`src/lib/task/result-projection.ts`；完整结果只在 `Task.result`。
- 批量聚合与恢复：`src/lib/project-agent/operation-batch.ts`、`src/lib/project-agent/waits.ts` 与既有 Task terminal continuation。
- 运行展示最终 View：`src/lib/project-agent/session-state.ts`、`src/lib/project-agent/subagent-events.ts`；生产 UI 只消费该 View。
- Story Canon 与 Chapter 独立采用入口由各自 Operation/service 拥有；正式事实读取与 revision 校验在 `src/lib/edit-chapter/creative-context-service.ts`，最小上下文纯派生在 `src/lib/creative-worker/context-compiler.ts`。读取 service 不能改写 Chapter/Story Canon/Resource，纯 compiler 不能访问数据库。
- 主 Agent 运行规则：`src/lib/ai-prompts/templates/project-agent/system/**`；它只声明何时规划和委派，不复制 Skill 正文。

## 生命周期

1. 主 Agent 从正式项目 View/Resource 读取目标所需事实；复杂任务可先用 `update_plan` 记录非权威计划。
2. 主 Agent 调用 `delegate_creative_work`：`delegation.source=requests` 传入一个或多个独立上下文；只有已经存在多个 Chapter 且独立工作单元适合并行时，才可选 `delegation.source=chapters`，由 Context Compiler 为每个 Task 构造最小上下文。这是批量输入助手，不是时长分支或工作流。
3. Operation 从正式 `analysis` 角色配置解析并冻结模型与 Skill 版本指纹，同时只读一次当前 adopted Creative Direction，并按 output registry 向每个非方向生产者请求注入同一份完整精确内容，再经统一 Task submitter 创建 `creative_work_v13` Task；所有成员加入当前模型步骤的唯一 OperationBatch/collecting Wait，前台只收到 durable receipt，不被阻塞。Task 内方向 Resource 与内容在创建时冻结。
4. text worker claim 某个 Task attempt，Task handler 启动一次无状态 Worker。Worker 自动读取拥有通用事实纪律与时长估算方法的 `creative-core`，再读取 registry 绑定并作为唯一目录项提供的专业 Skill；Skill trace 与生成/研究/提交校验阶段以小型 lifecycle projection 更新同一 Task。只有方向 Task 同时得到受预算约束的 Web Search，并把网页视为不可信证据。
5. Worker 返回 strict output；handler 校验 output kind、结构、预算、真实 Skill trace 与运行时研究证据，把完整结果写入 `Task.result`，终态事件和 continuation 只携带 reference projection。
6. 全部批量成员终态后，collecting Wait 只恢复主 Agent 一次。主 Agent 按 taskId 读取所需完整结果，再通过既有 Operation 唯一入口采用 Story Canon、建立/修改 Resource、生成媒体或继续规划。

Primary 对每个目标评估独立工作单元、共享 canon、跨单元状态、上下文大小、并行恢复价值和用户意图。总时长大于 180 秒只是应认真评估全局连续性与 Chapter 的强信号，绝不是代码分支；短作品也可因多条并行叙事需要连续性，长作品也可在单一连续上下文中完成。对用户要求交付的 `>15s` 完整视频，Primary Prompt 另行要求在媒体执行前采用匹配 Direction 并创建最终视频实际使用的参考资产；该纪律不由 Worker runtime 执行，不改变 Creative Work 的合法性，也不产生自动下一步。Story Canon、Creative Direction、Chapter、连续性分析或任一 Subagent Task 都不自动调用下一步。

取消、超 turn、超 Skill 读取次数、Skill URI 非法、输出不合约或 LLM provider 失败只影响当前 Task attempt，并继续服从 Task retry/terminal 规则。方向研究的 Web Search 不可用、失败或预算耗尽则按 CS-06E 记录显式 evidence/warning，不能伪装成功，也不把仍可基于用户事实与 Skill 生成的方向 Task 改写为 provider 失败。Worker 自己没有 retry、Wait 或补偿权。失败不会写领域事实；是否重新委派由主 Agent 在 continuation 或后续用户 turn 中显式决定。

## 验证

- `tests/contracts/project-agent-toolset-conformance.test.ts` 从生产 Operation registry 证明唯一委派 Operation 进入完整 toolset，并验证 strict `delegation.source=requests|chapters` schema。
- 同一 Conformance 还从 `creativeWorkOutputRegistry.workerTools` 穷尽证明只有 `creative_direction` 获得 `web_search`；研究协议、provider wire 和 generation metadata 分别由 Web Search 模块列出的 Logic/Critical contract 承担。
- TaskDefinition conformance、OperationBatch/Wait Critical 场景和 Assistant Session/Task SSE 场景是 Task 生命周期与聚合语义的适用证据。`GJ-FREEFORM-RESOURCES` 必须证明 Episode 对话发起的项目级 screenplay Subagent 在 UI 可见；`GJ-PROVIDED-SCREENPLAY` 必须证明当前用户原文直接写为项目级通用文字且不创建 Creative Task。
- TypeScript 与 ESLint 只能验证类型和结构；它们不能证明真实外部模型一定服从绑定 Skill、做出合适的连续性/Chapter 判断或产出高质量导演结果。

## 历史回归

- 2026-07 的视频链路重构曾一次性缩短主 Agent Prompt，并连带删除 Choice、Task continuation、失败边界等仍有效运行规则；真实模型随后遗漏 Choice，deterministic provider 又无法反证。Creative Skill 迁移不得重演“删除大段 Prompt 等于迁移”：当前防线先分类运行规则、专业知识、严格 adapter、确定性 builder 与确实 obsolete 内容，只有 owner 已替换的创意 Prompt 才删除。
- 初版 Creative Worker 把 Subagent 作为同一 Tool call 内同步 Activity，`ProjectAgentActivity.id`、`subagent.progressed` 和 response data part 共同解释运行态；它不能后台存活、不能批量聚合，也会把长输出直接带回模型上下文。当前一次性删除该解释权：Task.id/status 是唯一身份与状态，OperationBatch/Wait 是唯一聚合恢复，Task.result 保存完整输出，Session/continuation 只收 reference projection。
- 视觉专业知识最初合并为 `visual-development`，同时包含全局风格裁决与角色/场景/道具生成，导致资产修改可能反向改写 Creative Direction。当前删除旧 identity，并分别由 `creative-direction` 与 `asset-development` 独占职责；资产可独立工作，但提供确认风格时只能消费该事实。
- 目标分支曾把从零写剧本、剧本登记、风格与资产串成固定 00–07S 管线，并允许 Worker 给出最终实体 key；首次自由化虽然删除了确认状态，却仍要求用户粘贴的完整剧本先经过 canonicalization 才能作为剧本存在，保留了一个换名后的固定前置。当前用户原文由既有 `create_text.current_user_text` 精确保存为 screenplay，创作剧本只由 `story-development`，方向与剧本顺序独立；`asset-development` 消费精确 screenplay，并在服务端实际注入完整 Direction 时自行使用与资产相关的政策。真实模型对别名归一、一次性关键空间和资产范围的筛选质量仍是生成复验盲区；物化层只拥有确定性 manifest identity、名称歧义与输入 Lineage，不伪装成语义裁判。
- `asset_manifest` 第一版把 `sourceRefs/sourceExcerpt/reason` 当作来源防线：Worker 重新抄写剧本原文，终态用逐字符 `includes` 校验。它只能证明某个字符串存在，不能证明所引内容支持对应资产；模型对引号、标点、换行或空格的轻微改写却会让整份 Task 失败。旧测试只覆盖手写精确匹配和明显虚构字符串，没有经过真实模型复制漂移。当前从 strict output、Skill、物化校验、测试夹具和架构契约完整删除这些字段；精确 screenplay Resource 与 Lineage 只证明实际输入，资产选择继续由唯一 `asset-development` Worker 裁决。`creative_work_v8` 不兼容 v7，部署前排空旧 Task/Wait，不保留双 schema。
- Creative Direction 从旧 Style Bible 继承了“final 或候选集合”的联合输出；后来把候选上限从 12 降到 3，只限制了数量，没有消除同一任务并行写多份六领域政策的根因。真实约一分钟方向任务仍会生成三套完整方案并在 structured output 阶段消耗大量时间；旧 Golden 只走 `final` fixture，schema Logic 只验证空候选被拒绝，因此没有反证多版本真实路径。当前 `creative_work_v9` 直接要求一份 `creativeDirection`，删除候选 identity、候选物化和多资源结果字段；一个 Task 只写一个 Resource。v9 部署前必须排空 v8 queued/processing Task 与 Wait，不保留双 parser；真实 provider 的输出服从度与耗时仍需生产抽样验证。
- 旧视觉 Bible 只有资产清单路径会显式核对 adopted Binding；其余 Subagent 依赖 Primary 手动复制，Chapter compiler 又按引用列表条件式拼接，导致同一方向事实有多个注入者、不同门槛，并且换绑可能被不同路径以不同时间读取。把所有 Worker 改成主动读取 Project Context 会扩大无状态 Worker 权限，也会让每种 Worker 重复版本判断。第一版统一注入仍按 output kind 裁剪六领域，结果让影视各工种之间的关联被服务端静态预判，`chapter_plan/continuity_analysis` 甚至完全看不到方向。当前删除领域投影与字段清单，只保留 output registry 的布尔注入政策：`delegate_creative_work` 在 Task 创建时一次读取并向全部非方向生产者冻结同一份完整内容；Worker 自行判断相关性，Primary 手动引用方向、Asset 特殊核对和 Chapter 方向旁路继续 fail closed 或删除。`creative_work_v7` 不兼容 v6，部署前排空旧 Task/Wait。
- Resource 曾同时要求 `resourceId + revisionId + fingerprint`，调用方还可附带一份来源文本；第一次收敛只保留 revisionId，仍留下 Resource 与 Revision 两层身份。当前跨层输入只保留短 resourceId，内容直接属于该不可变 Resource；Task 幂等 hash、Choice subject snapshot 与 SSE event identity 仍是各自协议的内部防重/防旧事实，不属于 Resource identity。
- 后续为自由创作补充图片与视频方法时，详细专业知识全部常驻主 Prompt，使简单请求也支付整份上下文成本，并让主 Agent 同时承担编排与专业创作。当前主 Prompt 只保留委派纪律，专业方法由 Worker 按需读取；Worker 没有项目写权，因此不会形成第二业务 Agent runtime。
- 一分钟视频真实请求曾由 Primary 在委派前硬编码“6 段、每段 10 秒”；首次防线又以 15/180 秒三个区间写出唯一 Playbook，并把 Creative Direction/Chapter 变成服务端前置，仍然是换名后的串行架构。当前删除固定段数、逐段时长、Chapter 与 continuity 路由：Primary 依据独立工作单元、共享 canon、上下文和恢复价值判断是否使用 Story Canon/Chapter/连续性分析，`>180s` 只提醒评估且不能触发代码分支或 WorkerGroup。产品后来明确要求 `>15s` 完整视频在媒体执行前先采用 Direction 并建立最终成片会用的参考资产；这条窄化纪律只存在于 Primary Prompt，不进入 Operation schema、Worker runtime 或服务端 eligibility，也不规定段数，因此不恢复旧三档 Playbook。
- Skill + Subagent 路径上线后，旧 script intake、Story Canon generator、风格预览 Choice、Chapter/shot writer、资产 AI writer 与 BGM planner 仍以“专业主链”保留；Task 成功 Resource 与旧领域确认事实形成双轨。当前切换删除全部旧创意 LLM writer：Creative Worker 是专业判断唯一 owner，Operation 只负责确定性采用和执行，通用 Choice 只负责当前决定。
- 首次试图约束视频导演质量时，`video_prompt_set` 同时输出 `globalDirection + directorTimeline + finalPrompt`；运行时只能证明时间线连续覆盖，却无法证明平行字段中的专业判断真的进入最终视频模型输入，Primary 还必须再次理解或总结这些过程字段，形成两个竞争的创意表达。真实成功样例只消费每段最终 Prompt，并已把入口/出口状态、可见动作、逐字对白、同步声音和接缝设计直接写入其中。当前删除所有平行过程字段，以唯一 `prompt` 作为创意指令权威；strict schema 只保留执行元数据，Skill 通过完整示例约束内化质量。真实外部模型能否长期稳定遵守仍需手工复验。
- 条件式转场初版只要求描述前镜终点与后镜起点，没有显式拒绝叠化；真实视频模型即使没有收到“叠化”字样，也可能按生成先验自行使用交叉溶解、淡入或淡出。黑暗示例中的“降至全黑、逐渐揭示”还会放大这一倾向。当前防线要求每份多 Shot 最终提示词携带固定禁止句，把黑暗衔接限定为场景内真实变暗后清楚切换，并由双语 Skill guard 锁定；真实外部模型服从性仍需生成复验。
- 同场景、同人物的相邻独立片段曾以近似宽幅构图衔接，人物却从画面边缘跳到中央。旧 Skill 只要求前段末镜头与后段首镜头具有“景别或角度差异”，Worker 以宽幅侧景到宽幅背景满足字面要求；旧语义 guard 也只证明泛化规则存在，不能反证同景别换角度和缺失站位锚点。当前防线删除该二选一表述：最终输出前逐对检查全部独立片段接缝，前后必须形成真实可见的不同景别，角度变化不能替代景别变化；需要站位的首尾画面以稳定实物锚点、画面区域或纵深、朝向和道具关系正向描述，并由双语成对示例与现有 Skill guard 锁定。`video_prompt_set` 仍只消费唯一 `prompt`，没有新增过程字段；真实外部视频模型对空间指令的服从度仍需生成复验。
- 上一条接缝防线只有空间维度，同一不变量随即换形式复发：真实成片出现「掌面拍在桌上」紧接「手掌在桌面上的特写」这类同一动作节拍被重看一遍的卡顿剪法。它通过了当时全部检查——身份、服装、道具、站位连续，景别也确实不同——因为规则里从来没有时间维度，`video-direction` 甚至主动建议用「有信息价值的道具或动作特写」制造景别差异，等于把换景别重看同一瞬间列为推荐做法。同期暴露的第二个缺口是构图：主体落位、机位角度与视线落点在两份 Skill 中都写成「站位影响构图时才写」的条件项，Worker 判断不需要就整段留空，而角色资产板固定版式本身是正面居中、中性表情、直视镜头，缺少正向构图指令时视频模型直接继承，产出人物永远居中并盯着镜头。当前防线：接缝检查改为景别差异加时间递进两个必要条件，同一节拍禁止复现；切点按边界类型分层，段内可切在动作进行中、跨段必须落在完成落点，避免用 cut-on-action 去撞「不把未完成动作切到两次独立生成」这条既有铁律；主体落位、机位角度与视线落点升为每个有人物镜头的必写项，并新增与叠化禁令同级的固定句「人物视线落在场景内明确对象上，不与镜头交汇。」；参考图只提供身份、不提供机位构图姿态视线写成正向硬约束；新增示例四同时示范段内 cut-on-action 与「时间回退」「无动机居中直视」两个成对反例，因为上两次都证明纯禁止句会被字面满足而示例会被模仿。新句子已逐条钉入语义 guard，防止下一次重写静默删除。`video_prompt_set` 仍只消费唯一 `prompt`，没有新增过程字段；真实外部视频模型对时间与构图指令的服从度仍需生成复验。
- 同一次真实视频提示词任务只读取了 `video-direction` 与连续性知识，漏读了当时承载通用导演方法的 `director-core`；第一轮防线把多 Skill 组合写进摘要和正文，随后把导演知识合并进唯一 `video-direction`，但又在 2026-07 重构中删除 `requiredSkillIds`，改成“全量目录 + 模型自主选择 + 跨域可多读”。真实 `creative_direction` 目标提到镜头、资产和声音后，模型据此合法加读 `asset-development` 与 `video-direction`；目录文案只表达必读下限，没有任何排他门禁。当前 `professionalSkillId` 回到 output registry 作为唯一权威，目录、Tool 参数与终态 trace 校验均从它派生；模型既看不到也读不了其他专业 Skill，不再用自然语言纪律承担选择正确性。

- `video_prompt_set` 请求曾把 `targetDurationSeconds` 定义成必填精确秒数：用户没有说明时长时 Primary 只能猜，运行时又要求分段之和精确等于该数字，猜大的部分只能由重复动作和拖慢的表演填满，真实短剧因此被拉长近一倍。旧防线只在 Prompt/Skill 层约束估时口径，无法表达“用户没有指定时长”，也不能阻止规划估时被当作交付预算。当前请求契约改为显式 `durationIntent`：`mode=fixed` 承载用户明确说明的秒数并保持严格等值校验，`mode=derive` 让导演 Worker 从真实对白语速、可见动作与必要停顿决定总时长；schema 对 `video_prompt_set` 强制要求该字段，缺失 fail closed。Skill 同时补齐可执行估时口径（语速折算、并行内容取最长不累加、停顿预算、题材节奏档位、加速与必须保留清单）和反向注水检查。真实模型的估时准确度与慢戏是否被误压缩仍需抽样验证。
- 通用语速与表演时长方法首次放在 `continuity-memory`，registry 摘要还宣称它拥有全系统唯一口径；`story-development` 又显式指路，导致仅需写 60 秒剧本的 Worker 也会合理地额外读取连续性 Skill。旧设计保证了数字唯一，却把通用知识放进了错误的专业 identity，增加上下文并混淆“时长估算”和“连续性事实”。当前完整通用方法位于每个 Worker 自动预加载的 `creative-core`，`continuity-memory` 只服务 `story_canon/continuity_analysis`；screenplay 系列复用事实由请求中的 Resource/Context 提供，不构成额外 Skill 例外。
- 人物安全约束曾只在 Primary System Prompt 末尾存在，Creative Worker 不读取该 Prompt；而 CS-11 又禁止 Primary 用另一个模型重写最终 `generationPrompt`，导致“事后修正”与唯一创意 writer 冲突。第一次纠正要求 Primary 在委派 Direction/Manifest 前把明显风格化、非照片写实的人物身份约束手动写入请求，但这仍把正确性交给主模型是否记得转述：Primary 与每个 Creative Worker 是隔离模型循环，父级 system prompt 不会继承，Task JSON 也只携带模型实际提交的 constraints，真实方向 Task 因而仍可能完全看不到该规则。当前 `creative-direction` v4.1 把人物必须非真人、非真实人脸、非公众人物、非数字人、非照片写实且非写实人形 CG 写为 `visual.visualStyle + assetPolicy` 的必备政策和提交前自检；监控/VHS/纪录片/档案质感只能作用于环境、镜头与媒介表面。新 Direction 通过既有完整 adopted Direction 注入传给下游 Worker，不再依赖 Primary 逐字复制专业政策；旧 Direction、没有 adopted Direction 的独立下游任务，以及真实模型是否读取并服从该 Skill 仍是生成复验边界。
- Subagent reasoning/轨迹第一次实现把 snapshot 事件分别定义在 runtime、Task contract 与 UI parser 三处，且真实 OpenRouter 请求未获取公开 summary；测试虽通过，真实运行只留下 Skill 事件、reasoning 为空，最终被整体回滚。当前 `trace-contract.ts` 是唯一持久事件 schema，Primary 与 Worker 共用公开 reasoning normalizer；Worker delta 走既有 Task stream，durable block 与 tool 状态只由 handler 写同一 lifecycle projection，真实 Provider 与 UI 组合仍是发布验证边界。
- Creative Worker 最初把权威 Zod schema 原样交给 Agents SDK；本地 Golden Provider 接受完整 JSON Schema，因此测试没有反证 OpenRouter 路由到 Azure 后会拒绝 `minimum`、`minItems > 1` 等关键词。第一道修复删除动态 `outputType`，改成固定 `submit_result({outputJson:string})` 并在 Tool 内同轮校验；它恢复了纠错入口，却把整份对象再次编码成模型手写字符串。真实方向任务在 197 秒后提交的 7,450 字符字符串少一个右花括号，Tool 只能返回根级 `invalid_json`，随后 97 秒纠正轮被 5 分钟 deadline 截断；本地 lifecycle 又静默丢弃 submit error，只能从外部 Trace 还原。v12 删除字符串却保留 `submit_result({output:{...}})` envelope，单元模型与 Golden provider 也同步生成该 envelope，只证明了测试实现自洽；真实 Claude 剧本任务连续三次调用均因服务端读取不到 `output` 而以根级 undefined 被拒，第四次才通过，而持久日志只留下 `outputChars=0` 与 Zod issue，无法回答原始参数究竟是根对象、空对象还是错误字段。当前 v13 让 canonical 结果对象本身成为 Tool 参数根，删除 envelope；拒绝 trace 同时保存原始参数字符数、JSON 类型、顶层字段总数与有界字段名，不保存值或候选正文。Logic 反例直接提交旧 `{output:...}` 并要求拒绝，Golden provider 直接提交 schema 生成的根对象；真实付费 Provider 对大对象 Tool 参数与多轮纠正的服从度仍是发布复验边界。
- Resource named-link 终态投影曾同时把 materialized refs 写到 Task 根级 `resources` 与模型 continuation 的 `continuationProjection.resources`，却只扩展了前者的 strict schema；Worker 与终态事务都成功后，Session 再读同一 completed Task 反而因未知字段 fail closed。此前 fast suites 只构造 materializer 前的 Task result，而目标 Golden 又停在更早的画幅 Choice，未覆盖“Worker accepted result → terminal materializer 增广 → Session strict parse”的真实组合。当前两处复用同一个 materialized Resource schema，并要求 continuation refs 与根级 refs 完全一致；生产 conformance 同时反证未知字段和两份精确身份漂移，Golden 覆盖终态后 Session/链接交付。
- Subagent UI 初版按 `Task.episodeId` 查询 Task，而 Project 级 `screenplay/creative_direction` Task 的该字段为 null；即使 `payload.origin.runId` 明确属于当前 Episode Run，刷新和终态 UI 仍会把它排除。现由服务端以 Assistant Run 的 `assistantId + scopeRef` 和 immutable `payload.origin.runId` 投影 SessionState.subagents，客户端 stream 只接受其中 taskId；Task episode 只保留输出 Resource scope 语义。Golden 对项目级 screenplay Task 的可见 tab 是反证防线。

- Creative Worker 曾在 handler 内复用全局 20 分钟外部 timeout，而通用 worker 每 10 秒无条件刷新 heartbeat；`maxTurns=8` 只限制模型循环次数，不限制单 turn 墙钟时间，因此一个仍在 BullMQ 中存活但不再产出事件的调用可以长期显示 processing。第一道治理把 5 分钟 execution deadline 登记进 TaskDefinition，解决了“永久 processing”，但真实合法方向任务的首次对象生成加一次校验纠正恰好需要约 300 秒，安全阀变成了正常路径裁判。当前 deadline 仍由 TaskDefinition/attempt owner 单一持有并保留 typed `GENERATION_TIMEOUT` 与 terminal fence，只校准为 20 分钟 safety bound；`maxTurns` 继续只承担循环/成本上限，heartbeat 和 UI 阶段事件都不解释完成。
